Anatomy of a memory access on the ET-SoC-1

19 September 2026 · aifoundry2's card · minion clock 600 MHz, NoC 400 MHz, LPDDR4X at 3,733 MT/s · workload workloads/memprobe · part of the ET-SoC-1 measurement reports

How finely can this chip show you where a load's time and energy go? For time, the answer is one cycle, for a single load. You can put any one line in L1, L2, L3 or DRAM, time one load of it, and split the result into cache lookups, mesh hops, the memory controller and the DRAM row state. A model built from those parts predicts each line's DRAM latency to within ±3 cycles for 97% of lines. Of a typical DRAM load's ~300 cycles, only about 25 are the DRAM chip's own timing; the rest is paths on the chip. For energy, the finest view is four destinations: the minion cores, the SRAM arrays, the mesh (NoC), and the rest of the board, which is mostly the DDR side. The first three are metered rails; the rest is the board total minus those three. The meters give a new value every 133 ms, so each energy number is an average over billions of identical loads.

Later measurements. The energies in §7 are superseded by later measurements on two cards, with zeros and with random data: the energy manual (§4) and Heat per millimetre. The manual puts a DRAM read at 122 pJ per byte against 79 here, and on random data both put a mesh hop at about twice this page's 0.9 pJ per byte. The last note in §7 compares the numbers. The latencies are not affected.

Terms. The ET-SoC-1's compute cores are minions: small in-order RISC-V cores, each with two hardware threads (harts) and its own L1 cache. Thirty-two minions form a shire, and each shire's 4 MB of SRAM is split into a 512 KB L2 cache, a 1 MB slice of the chip-wide 32 MB L3 and a 2.5 MB scratchpad (software-managed memory that any shire can address). The 32 compute shires, with the master, spare, I/O and PCIe shires, form a 6×6 grid on a mesh network-on-chip (the NoC, 400 MHz); eight memory shires, which hold the LPDDR4X controllers, sit outside the grid on two sides. Every cache line has one L3 home shire, chosen by its address bits, whose L3 slice holds it. Kernels run in user mode (U-mode) and firmware in machine mode (M-mode); the service processor (SP) is the on-die management core that reads the power sensors. More in the hub's glossary.

1. What the chip lets you see

Everything here runs as an ordinary user-mode kernel through the runtime, on the card's installed firmware. The firmware source read for this work is et-platform 353f20e; the cards' own trace strings match an older build, from before et-platform commit 60b40c10f (24 September 2024). 3. The ladder, one load at a time

For each of 64 random lines, one hart loaded the line, evicted it to a chosen level, fenced, waited 300 cycles, and timed one load. Values are load-to-use cycles: the raw reading minus 5, an offset chosen so an L1 hit reads the 5 cycles the memory-hierarchy report's pointer chase measured. (A timed no-op and a timed L1 hit both read 10 raw; the offset moves every absolute number but none of the differences between levels.) The spread at L3 and DRAM is almost entirely distance on the mesh (§4, §5), not noise.

Load-to-use latency by where the line was left (cycles at 600 MHz, 128 loads each)

* One of 128 dirty evicts took 16 cycles, as fast as a clean one (no write-back); the rest took 112–480.

Evicts keep working after the instruction retires, but none of the 256 loads timed straight after an evict to memory came back in L3 time: every one went to DRAM. What changes is the timing. With no fence, the load queues behind the evict (median 365, about 58 cycles above the §5 model). With a fence but no wait, a third of the loads find the row that the previous load of the same line opened still open, and read 11 cycles fast (minimum 213, on a line whose closed-row time is 225). With the fence and the 300-cycle wait, none read fast: 115 of 128 land within ±6 cycles of the §5 model, which is the closed-row time, and the rest are slower.

The memory-hierarchy report's pointer chase, run the day before with the clock not pinned, agrees: its DRAM chases took 287–297 cycles (480–495 ns) when the minions ran at 600 MHz, and 352–368 cycles (440–460 ns) when the governor had raised them to 800 MHz. Every load on this page ran at a steady 600 MHz (the refresh period in §6 matches the DRAM's refresh interval only at that clock).

4. L3: 110 cycles plus 12 per hop

Each line's L3 home shire is picked by physical-address bits 10:6. From shire 0, 1,500 random lines were timed as L3 hits. Latency depends only on the home shire's Manhattan distance on the mesh: 110 + 12 × hops, within ±4 cycles for 1,498 of 1,500 lines (the median of three loads per line; 1,309 are within ±2). So a local L3 hit costs 110 cycles: ~48 for the L1 and L2 lookup and miss, ~62 for the home slice. Each hop adds 12 cycles (20 ns) for the request and the reply.

L3 hit latency from shire 0 against distance to the home shire (one dot per home shire)

L2 hits in the same run come in two flavours: 37 cycles when the line is still in the bank's 8-entry read buffer, and 48 from the array.

5. The memory shire leg: 91 cycles plus 12 per hop

The same 1,500 lines were also timed from DRAM (each load at least 1,000 idle cycles after the row was last used, so the row had closed and every load paid an activate; no contention), and each line's L3 time was subtracted. What remains is the leg from the home shire to the memory shire and back. The memory shire is picked by bits 8:6. The hardware counters confirm it: for all 64 lines tested, 16 DRAM loads raised the read count of the shire named by those bits, by 16 for 60 lines and by 15 for 4. The other seven shires' counts didn't move (one stray count of 1 in 448).

The fit uses one shared constant plus 12 cycles per hop. Assuming each memory shire hangs one hop outside the grid (the only positions the fit tried; moving all eight one hop further out fits equally well with a constant of 79), the best fit puts memory shires 0–3 above the grid and 4–7 below it, at x = 1…4. The total squared error is 2 cycles² over 32 home/memory-shire pairs. The whole DRAM load is then

latency = 110 + 12·hops(requester → L3 home) + 91 + 12·hops(L3 home → memory shire)

and the model's error is within ±3 cycles for 1,450 of 1,500 lines and within ±5 for 1,490. The other ten are outliers: seven read about 128 cycles short (counter glitches the correction missed, §8), two are 44 and 71 cycles slow (probably refresh), and one is 29 cycles fast.

Measured DRAM latency minus model, per line (fastest of 3 loads)
Read-counter increase on each memory shire after 16 DRAM loads of one line (first 12 of 64 lines)

Of the 91 cycles (152 ns), the DRAM chip itself accounts for about 25: an activate (the activate-to-read delay tRCD, 11 cycles = 18 ns, §6) plus the 19.3 ns read latency and a 4.3 ns burst (14 cycles), from the controller's timing registers. The remaining ~66 cycles (~110 ns) are the memory shire: controller queue, PHY, and the crossings between the 933 MHz DDR clock and the mesh. The frequency experiment in §9 would split this further.

6. Inside the DRAM: rows, banks and refresh

Which address bits share a row

A second load B was issued one cycle behind load A, with B = A with one physical-address bit flipped. Both were cold in DRAM, 150 random A per bit. When B shares A's row, or sits in another bank or channel, it rides along and arrives with A (~300 cycles). When B is in the same bank but a different row, the controller must wait for A's row to finish before opening B's: +40 cycles (67 ns) for every bit from 18 up. That matches the controller's mapping: bank = PA[12:10], column = PA[17:13], row from PA[18].

Latency of the second of two back-to-back loads, by the address bit that differs (median and 10th–90th percentile)

Refresh, caught in the act

Loading the same line from DRAM 19,000 times at random intervals, and folding the timestamps on a period of 2,325 cycles = 3.88 µs, shows LPDDR4X refresh (tREFI, the refresh interval, is 3.9 µs):

  • A load that arrives while refresh is running waits up to 210 extra cycles (350 ns). That's close to the 281 ns all-bank refresh time, and the wait shrinks as the load arrives later in the refresh window.
  • Refresh also closes the open row. The next load pays an activate, 215 → 226 cycles. That's 11 cycles = 18 ns, exactly tRCD, the activate-to-read delay.
  • With a fixed loop period of 576 cycles, a loop locks onto refresh: every fourth load is the slow one, and none ever lands inside the refresh itself.
DRAM latency against the load's phase within the refresh period (median and slowest per bin)

How long a row stays open

Open-row hits save 11 cycles. Only about two thirds of back-to-back pairs get the saving, and after 1,500–2,000 idle cycles almost none do. That is about twice as fast as refresh alone would close rows (after 1,000 idle cycles, 23% hits against 44%). The controller's registers set an open-page policy with no idle-close timer (docs/research/counters-and-dram.md), so something else closes rows; this experiment cannot say what.

7. Where the energy goes

Hart 0 of all 1,024 minions walked a working set sized to hit exactly one level, with no evicts. The loop was the same six-instruction body for every level, run for 6 s per pattern, twice each. Power above the level just before each run, divided by the load rate, gives energy per load. The split comes from the service processor's trace: minion cores, SRAM (the L2/L3/scratchpad arrays), NoC (the mesh), and the rest = board total − those three rails. The rest is mostly the memory shires, DRAM, PHY and I/O. It also holds the regulators' delivery losses on the three metered rails: later work puts them at about 18–20% of the minion rail's power, 5–6% of the SRAM rail's, and part of the 26–29% it attributes to the mesh rail (see the hub's §4.2).

  • An L2 hit is mostly SRAM: 112 of 183 pJ, 1.75 pJ per byte. The core's share rises from 41 to 64 pJ because it spends longer stalled.
  • An L3 hit costs 3× an L2 hit even locally. SRAM goes to 306 pJ, for the L2 miss, the L3 read and the L2 fill, and the NoC rail appears at 120 pJ.
  • Each mesh hop costs about 59 pJ per load (per 64-byte line moved), 47 pJ of it on the NoC rail: going from a local to a far home (5.6 hops on average) adds 333 pJ. That is ~0.9 pJ per byte per hop.
  • A DRAM load costs ~5.1 nJ, and two thirds of it, 3.4 nJ = 53 pJ per byte, is off the metered rails, mostly on the DDR side. The mesh adds 0.9 nJ, because the request crosses the chip twice. The DRAM row itself could not be isolated: a pattern that conflicts on every access costs the same per load as a sequential one. With 1,024 streams interleaved, the sequential pattern probably re-activates rows on almost every access too.
  • Totals from the host's board-power log are 16–25% higher than the trace's own board average for every pattern (16–19% for L2, own-shire L3 and both DRAM patterns; 23% for L1 and 25% for far L3). Mid-run the two agree to within 0.3 W; the gap comes from the edges of each window. The trace's values are the power-management controller's running averages (τ ≈ 1 s; Power and temperature, §2), and as lined up with the host log the trace starts to rise about 0.7 s before each load process starts and to fall before the run ends. So its baseline reads high and its run average low. The table gives both; the split uses the trace so the parts add up, but the host log's totals are the cleaner measure of the whole.
  • Later measurements put DRAM higher. The energy manual (§4), measured on 23 September on both cards at a pinned 600 MHz with the host's board power, gives 122 pJ/B [117–129] for DRAM read by 1 KB tensor loads over memory whose contents were not set, and, with the data known, 91 pJ/B on zeros against 129 on random data. This page's 79 pJ/B was measured differently: its loads are 8-byte lds that each bring a 64-byte line through the caches; it uses the service processor's trace, whose rise above idle is 14–20% smaller than the host log's (with the host log it is 92 pJ/B); and its arena was never initialised, so the bit pattern of the loaded data is unknown. Per mesh hop the manual's 1–8-hop fit (§4.3) gives 0.64–0.75 pJ/B on zeros and 1.67–1.81 on random data across the two cards (2.1–2.3 on random data over 1–6 hops), against ~0.9 here; Heat per millimetre measures 1.5–2.2 pJ/B per hop on random data and splits it into flips and ones carried.

8. A timer bug worth knowing

Before anything above was trustworthy, the cycle counter needed fixing. 16% of back-to-back read pairs (320 by +138 and 314 by −118, of 4,000) differed from the expected 10 cycles. The raw values show what happens: a read whose low 7 bits are 0–10 is 128 too small, because the carry into bit 7 lands 11 cycles late. A simulation of the open RTL shows why: twelve counters share one adder that folds overflows in round-robin, and a read ignores the pending overflow (hub §3). This isn't erratum 1.23 (RTLMIN-6496, two harts reading counters at once): only one hart read here.

The firmware's four-reads workaround doesn't fix it. Adding 128 to any read with low bits 0–10 does, for all 4,000 pairs. Inside a running kernel it catches most but not all of them (see §1); the seven lines about 128 cycles fast in §5 are such misses, picked out by taking the fastest of three loads. Any code that times short intervals with hpmcounter3 on this card needs the same correction (see fixcyc() in workloads/memprobe/kernel/memprobe.c).

9. What would split it further

  • Clock domains. Set the minion and NoC clocks separately (DM_CMD_SET_FREQUENCY -f minion,noc, with DVFS off) and rerun §4–5. Each stage's cycles then split into minion-clock, NoC-clock and fixed-time parts, for example the 66 cycles in the memory shire. The hop cost is already known to be on the mesh clock: 20 ns per hop at 600, 700 and 800 MHz (on-chip communication report), so only the 110- and 91-cycle constants remain to split. It changes a shared card's state, so it waits for approval and a quiet card.
  • Static against dynamic energy. The same frequency sweep at fixed voltage gives each rail's C·V²·f slope. The DVFS report has since separated static from dynamic power another way, as a leakage law in temperature (23.3 W at 80 °C).
  • DRAM activate energy, and cache hit/miss counts. Both need counters that only M-mode can program. A user-mode syscall that sets them has been written and works in the simulator (sys_emu); running it on the card needs a signed firmware image, which is not available.
