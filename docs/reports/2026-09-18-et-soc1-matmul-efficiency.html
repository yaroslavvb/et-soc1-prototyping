ET-SoC-1 on real silicon: hello world, then matmul speed and energy efficiency vs the A100

Measured 18 Sep 2026 on aifoundry2 in the AI Foundry lab: one ET-SoC-1 PCIe card, 32 GB LPDDR4X, minion clock 600 MHz. Code in the nekko workspace (kernels/mmbench).

A tensor-unit matmul kernel on all 1,024 compute minions sustains 9.5 TFLOP/s in fp32, 19.0 TFLOP/s with fp16 inputs and 71.8 TOP/s in int8. That is 91–97% of the tensor unit's peak at this clock, and every result is checked bit-exact against a host reference. The card draws 57–62 W doing it, against 30.6 W at idle. Compared with the A100's spec sheet (peak ÷ TDP), ET-SoC-1 is 3.4× more energy-efficient at full fp32 precision. At fp16 and int8 the A100's tensor cores win on efficiency (2.4× and 1.3×) and by a much wider margin on raw speed (16× and 8.7×).

What I did

  1. Access. I logged in over Tailscale SSH as a personal non-root account. It had to be created on aifoundry2 first: Tailscale SSH rejects a user that doesn't exist on the machine with the same "tailnet policy does not permit" message it gives for a made-up name. The machine runs x86-64 Ubuntu 24.04 with one card (/dev/et0_ops, /dev/et0_mgmt): PCIe Gen4, 32 GB, minion shires at 600 MHz and NoC at 400 MHz. Firmware is BL 0.20 and minion 0.23.
  2. Toolchain was already there. /opt/et is et-platform built from commit 353f20e (30 Dec 2025): RISC-V GCC 15.1, sys_emu, runtime, firmware and the upstream test binaries. It is not on PATH by default.
  3. Hello world as defined in et-platform's README (it_test_code_loading): 3/3 tests pass on the simulator in 110 s, about 34 s per test, almost all of it simulated firmware boot. The same binary with --mode=pcie passes 3/3 on the card in 0.6 s.
  4. et-testdrive (marty1885's minimal host+kernel project) builds unmodified against /opt/et. On the card all 64 harts of shire 0 print "Hello World from hart N", decoded in-process from the trace buffer. One catch: it opens the management node, which only one process may hold, so it fails with "Device or resource busy" while et-powertop is running. The upstream tests open only the ops node.
  5. Writing my own kernels with gp-sdk needed four fixes against this older install. All four are local to my copy of gp-sdk on aifoundry2:
    • Current gp-sdk requires et-common-libs' Erbium components, which the Dec 2025 install doesn't have. I pinned gp-sdk to 06605ab (24 Mar 2026, the last version before the Erbium changes) and made dnnLibrary and FFTW optional. Only the pre-generated matmul and the FFT example use them.
    • gp-sdk's GenericLauncher started sys_emu without firmware ELF paths. The simulated service processor then trapped at address 0 in a loop and wrote a 15 GB log in 10 minutes before I stopped it and deleted the log. The workspace's patches/et-platform-0002 (preload the firmware) fixes it.
    • Every gp-sdk kernel, including gp-sdk's own print.elf, died on launch with a U-mode instruction access fault at PC 0x40. Kernels are linked at address 0 and relocated by the runtime, but this gp-sdk links without -Wl,--emit-relocs, so the entry-point table kept its link-time address. Upstream restored the flag in 7e3b4c2 (2 May 2026), and I added it locally.
    • The old riscv_helpers.cmake uses CMake's plain target_link_libraries signature, which clashes with the workspace's keyword form. I switched it to the keyword form, as upstream later did.
  6. Wrote the benchmark: kernels/mmbench (device), launchers/mmbench (host, checks every result), scripts/et-power-log.sh (board-power sampler) and scripts/mmbench-power.py (runs everything and averages power over the launch windows). It passed exact checks on the simulator on one shire in all modes, then on the card on all 32 shires, before the timed runs.

How the benchmark works

  • The loop. On each of the 1,024 compute minions, hart 0 runs the loop; only hart 0 may issue tensor ops, so hart 1 idles. Each op issues a tensor_load of a 16×K A tile into one of two L1-scratchpad buffers, a tensor_load of the B tile through TenB, a tensor_wait, and a tensor_fma that accumulates a 16×16 C tile in the vector registers. The next op's loads overlap the running FMA. This is the inner loop of gp-sdk's auto-generated matmul and of the pipelined kernel in the FOSDEM 2026 "Zero to matmul" talk (10.25 TFLOP/s at 650 MHz).
  • Op size. One op is 16×16×K multiply-adds, with K = 16 (fp32), 32 (fp16) or 64 (int8). Operand layouts come from sw-sysemu's tensor emulation, which serves as the spec.
  • Working set. In the compute-bound runs all minions share 16 A/B tile pairs (32 KB), so the data stays in each shire's L2 cache. In the DRAM run each minion has its own 64 tile pairs (128 MB in total), so every load goes to memory. Effective read bandwidth there was about 78 GB/s.
  • Inputs and checking. Inputs are random values from {−2, −1, 1, 2}. They are never zero, so no multiply can be skipped, and they are exact in fp16 and fp32. The host checks each minion's C tile for exact equality with iters × Σ A·B, capping iteration counts so fp32 accumulation stays exact. Every launch passed with zero bad minions.
  • Power. Board power comes from the card's own telemetry (DM_CMD_GET_MODULE_POWER through dev_mngt_service, about 7 samples/s). It is averaged over the launch windows after skipping the first second. Idle is the median over 8 s before the first workload.

Caveats

  • The A100 figures are spec-sheet numbers, not measurements. Large GEMMs on an A100 typically reach 80–90% of peak while running near the power limit, so its delivered efficiency is lower than these ratios. The ratios here are a best case for the A100.
  • Board power includes the whole card: 32 GB LPDDR4X, voltage regulators and PCIe. The 30.6 W idle floor is over half the load power. The above-idle column (366 / 664 / 2,305) shows the cost of the compute alone.
  • One clock point. The lab card runs its minions at 600 MHz, and other clock and voltage points will change both speed and efficiency. Power rose about 3 W within each 12 s run as the chip warmed, so longer runs would read slightly worse.
  • Precision differs. ET's fp32 tensor op is a full IEEE fp32 multiply-add, whose A100 equivalent is fp32 on CUDA cores; tf32 keeps only a 10-bit mantissa. ET's fp16 op accumulates in fp32 with round-toward-zero.
  • Peak-rate microbenchmark. This measures the matmul engine on cached tiles. A full GEMM also pays for moving data, and the DRAM row (0.31 TFLOP/s) is the no-reuse floor.

Reproduce

# hello world from et-platform's README
/opt/et/bin/it_test_code_loading               # simulator
/opt/et/bin/it_test_code_loading --mode=pcie   # the card

# benchmark (nekko workspace on aifoundry2; quit et-powertop first)
nice make kernels launchers JOBS=4
python3 scripts/mmbench-power.py --launcher build/launchers/mmbench_launcher \
    --kernel build/kernels/nekko/mmbench.elf --out build/mmbench-power

The lab cards are shared, and the lab rule is to hold a device for at most 10 s. The run above kept the card busy for about 12 s per workload, before that rule reached this workspace. The script now runs every launcher under timeout 10 and defaults to about 6 s per workload, which still leaves roughly 35 power samples per workload after the settle time.
