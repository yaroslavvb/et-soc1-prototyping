# memprobe: one memory access at a time

Splits the latency of a single load into its stages (cache lookups, mesh hops, memory shire, DRAM row state), and
the energy per load into power rails. The results are in `docs/reports/2026-09-19-et-soc1-memory-anatomy.html`;
the survey of what the chip exposes is in `docs/research/counters-and-dram.md` and `docs/research/power-telemetry.md`.

The structure is the same as `workloads/memhier`: runtime API plus a minimal kernel, no gp-sdk, so it builds against
the lab machines' older `/opt/et`.

## Two modes

- **Op programs** (`--program x.ops`). One hart runs a list of ops generated by `gen_ops.py`: timed load, load,
  back-to-back pair of loads, `evict_va` to L1/L2/L3/memory, fence, delay, time stamp, store, and a read of a memory
  shire's hardware counter (syscall 10). The list is first copied into the shire's own L2 scratchpad and the results
  are recorded there, so the probe itself makes no DRAM traffic. Each timed op gives one u32 in `x.u32`, matched to a
  label in `x.json`. Addresses are offsets into an arena aligned to its own size (1 GB at `0x8040000000` on
  aifoundry2), so offset bits are physical address bits.
- **Power loops** (`--loop --table t.tbl --stride S --lines N`). Hart 0 of all 1,024 minions walks its own working
  set, sized to hit exactly one level, with no evicts, in the same unrolled six-instruction loop.
  `run_power.py` runs each pattern for a few seconds while logging board power, and extracts the service
  processor's per-rail trace. `analyze_power.py` turns that into pJ per load per rail.

| Experiment (`gen_ops.py …`) | What it measures |
|---|---|
| `timer` | The cycle counter: raw read pairs, and corrected timed no-ops (always 10 cycles) |
| `ladder` | One load after placing the line in L1 / L2 / L3 / memory; evict cost, clean and dirty |
| `decomp` | L2, L3 and DRAM latency of the same 1,500 lines: slice distance and memory shire leg |
| `msmap` | Which memory shire served a line, from its read counter |
| `bits` | Second of two back-to-back loads, per flipped address bit: rows, banks, columns |
| `refresh` (`--jitter`) | 19,000 timed DRAM loads of one line at random phases: the refresh period and stall |
| `pagetimeout` | Same-row second load after an idle gap: how long rows stay open |
| `table --pattern …` | Address tables for the power loops: `l1 l2 l3near l3far dram_seq dram_row` |

## Things this relies on

- `hpmcounter3` on this card reads 128 short when its low 7 bits are 0–10 (the bit-7 carry lands 11 cycles late).
  `fixcyc()` in the kernel corrects it. A timed load carries 5 cycles of overhead on top of the load-to-use latency.
- `evict_va` level codes name where the line is left: 1 = L2, 2 = L3, 3 = memory; 0 does nothing. It is
  asynchronous, so the programs fence and wait a few hundred cycles before timing.
- At full-chip scale, evicts serialize in each shire's cache (~3,800 cycles per load + evict per minion). That is why
  the power loops size their working sets instead of evicting.
- The service processor's stats trace is a 1 MB ring (~15 min). An extract returns only records since the last wrap,
  so `run_power.py` extracts after every pattern and the analysis merges the files. The extract does not reset stats.

## Run (on aifoundry2, card free, each process under `timeout 10`)

```bash
cmake -S workloads/memprobe -B build/memprobe -DCMAKE_PREFIX_PATH=/opt/et -Wno-dev && nice cmake --build build/memprobe -j4
mkdir -p build/memprobe-data && cd build/memprobe-data
python3 ../../workloads/memprobe/gen_ops.py decomp --out . --lines 1500 --reps 3 --pre-delay 1000
timeout 10 ../memprobe/host/memprobe_host --program decomp.ops      # 0.04 s of card time
```

The report's own commands are in its "Reproduce" section; `analyze.py` and `build_report.py` rebuild it from
`docs/reports/data/2026-09-19-memprobe-aifoundry2/`.
