Anatomy of a memory access on the ET-SoC-1

Measured on aifoundry2's card, 19 September 2026 · minion clock 600 MHz, NoC 400 MHz, LPDDR4X at 3733 MT/s · workload workloads/memprobe

How finely can this chip show you where a load's time and energy go? For time, the answer is one cycle, for a single load. You can put any one line in L1, L2, L3 or DRAM, time one load of it, and split the result into cache lookups, mesh hops, the memory controller and the DRAM row state. A model built from those parts predicts each line's DRAM latency to within ±3 cycles. For energy, the finest view is four destinations: the minion cores, the SRAM arrays, the mesh (NoC), and everything on the DDR side. The first three are measured rails. The DDR side is the rest of the board total. They update every 133 ms, so each energy number is an average over billions of identical loads.

3. The ladder, one load at a time

For each of 64 random lines, one hart loaded the line, evicted it to a chosen level, fenced, waited 300 cycles, and timed one load. Values are load-to-use cycles: the timed value minus the 5 cycles of timer overhead, which puts an L1 hit at the 5 cycles the pointer chase measured before. The spread at L3 and DRAM is almost entirely distance on the mesh (§4, §5), not noise.

Load-to-use latency by where the line was left (cycles at 600 MHz, 128 loads each)

Evicts are asynchronous. With no fence, the load after an evict to memory sometimes returns in L3 time (minimum 214 cycles against 226 with fence and wait), and the median rises to 365 because the load queues behind the evict. A fence alone is not enough either. Waiting a few hundred cycles makes the placement reliable.

4. L3: 110 cycles plus 12 per hop

Each line's L3 home shire is picked by physical-address bits 10:6. From shire 0, 1,500 random lines were timed as L3 hits. Latency depends only on the home shire's Manhattan distance on the mesh: 110 + 12 × hops, within ±2 cycles for 1,498 of 1,500 lines. So a local L3 hit costs 110 cycles: ~48 for the L1 and L2 lookup and miss, ~62 for the home slice. Each hop adds 12 cycles (20 ns) for the request and the reply.

L3 hit latency from shire 0 against distance to the home shire (one dot per home shire)

L2 hits in the same run come in two flavours: 37 cycles when the line is still in the bank's 8-entry read buffer, and 48 from the array.

5. The memory shire leg: 91 cycles plus 12 per hop

The same 1,500 lines were also timed from DRAM (row still open, no contention), and each line's L3 time was subtracted. What remains is the leg from the home shire to the memory shire and back. The memory shire is picked by bits 8:6. The hardware counters confirm it: for all 64 lines tested, 16 DRAM loads raised the read count of the shire named by those bits, by 16 for 60 lines and by 15 for 4. The other seven shires' counts didn't move. Fitting one shared constant plus 12 cycles per hop puts the memory shires one step off the north edge (0–3) and south edge (4–7) of the mesh, at x = 1…4. The total squared error is 2 cycles² over 32 home/memory-shire pairs. The whole DRAM load is then

latency = 110 + 12·hops(requester → L3 home) + 91 + 12·hops(L3 home → memory shire)

and the model's error is within ±3 cycles for 1,480 of 1,500 lines. The rest are outliers from refresh and timer glitches.

Measured DRAM latency minus model, per line (fastest of 3 loads)
Read-counter increase on each memory shire after 16 DRAM loads of one line (first 12 of 64 lines)

Of the 91 cycles (152 ns), the DRAM chip itself accounts for about 14 cycles on an open-row read: read latency 19.3 ns plus a 4.3 ns burst, from the controller's timing registers. The remaining ~77 cycles (~128 ns) are the memory shire: controller queue, PHY, and the crossings between the 933 MHz memory clock and the mesh. The frequency experiment in §9 would split this further.

6. Inside the DRAM: rows, banks and refresh

Which address bits share a row

A second load B was issued one cycle behind load A, with B = A with one physical-address bit flipped. Both were cold in DRAM, 150 random A per bit. When B shares A's row, or sits in another bank or channel, it rides along and arrives with A (~300 cycles). When B is in the same bank but a different row, the controller must wait for A's row to finish before opening B's: +40 cycles (67 ns) for every bit from 18 up. That matches the controller's mapping: bank = PA[12:10], column = PA[17:13], row from PA[18].

Latency of the second of two back-to-back loads, by the address bit that differs (median and 10th–90th percentile)

Refresh, caught in the act

Loading the same line from DRAM 19,000 times at random intervals, and folding the timestamps on a period of 2,325 cycles = 3.88 µs, shows LPDDR4X refresh (tREFI = 3.9 µs):

  • A load that arrives while refresh is running waits up to 210 extra cycles (350 ns). That's close to the 281 ns all-bank refresh time, and the wait shrinks as the load arrives later in the refresh window.
  • Refresh also closes the open row. The next load pays an activate, 215 → 226 cycles. That's 11 cycles = 18 ns, exactly tRCD.
  • With a fixed loop period of 576 cycles, a loop locks onto refresh: every fourth load is the slow one, and none ever lands inside the refresh itself.
DRAM latency against the load's phase within the refresh period (median and slowest per bin)

How long a row stays open

Open-row hits save 11 cycles. Only about two thirds of back-to-back pairs get the saving, and after 1,500–2,000 idle cycles almost none do. That is a little faster than refresh alone would close rows, so the controller may also close idle rows after roughly 2 µs.

7. Where the energy goes

Hart 0 of all 1,024 minions walked a working set sized to hit exactly one level, with no evicts. The loop was the same six-instruction body for every level, run for 6 s per pattern, twice each. Power above the level just before each run, divided by the load rate, gives energy per load. The split comes from the service processor's trace: minion cores, SRAM (the L2/L3/scratchpad arrays), NoC (the mesh), and the DDR side = board total − those three rails (memory shires, DRAM, PHY, I/O).

  • An L2 hit is mostly SRAM: 112 of 183 pJ, 1.75 pJ per byte. The core's share rises from 41 to 64 pJ because it spends longer stalled.
  • An L3 hit costs 3× an L2 hit even locally. SRAM goes to 306 pJ, for the L2 miss, the L3 read and the L2 fill, and the NoC rail appears at 120 pJ.
  • Each mesh hop costs about 59 pJ per 64-byte load, 47 pJ of it on the NoC rail: going from a local to a far home (5.6 hops on average) adds 333 pJ. That is ~0.9 pJ per byte per hop.
  • A DRAM load costs ~5.1 nJ, and two thirds of it, 3.4 nJ = 53 pJ per byte, is on the DDR side. The mesh adds 0.9 nJ, because the request crosses the chip twice. The DRAM row itself could not be isolated: a pattern that conflicts on every access costs the same per load as a sequential one. With 1,024 streams interleaved, the sequential pattern probably re-activates rows on almost every access too.
  • Totals from the host's board-power log are 15–20% higher than the trace's own board average, for every pattern. The two readings are filtered differently. The table gives both, and the split uses the trace so the parts add up.

8. A timer bug worth knowing

Before anything above was trustworthy, the cycle counter needed fixing. 8% of back-to-back read pairs differed by 138 or −118 cycles instead of 10. The raw values show why: a read whose low 7 bits are 0–10 is 128 too small, because the carry into bit 7 lands 11 cycles late. This isn't erratum RTLMIN-6496 (two harts reading counters at once): only one hart read here. The firmware's four-reads workaround doesn't fix it. Adding 128 to any read with low bits 0–10 does, for all 4,000 pairs. Any code that times short intervals with hpmcounter3 on this card needs the same correction (see fixcyc() in workloads/memprobe/kernel/memprobe.c).

9. What would split it further

  • Clock domains. Set the minion and NoC clocks separately (DM_CMD_SET_FREQUENCY -f minion,noc, with DVFS off) and rerun §4–5. Each stage's cycles then split into minion-clock, NoC-clock and fixed-time parts, for example the 77 cycles in the memory shire. It changes a shared card's state, so it waits for approval and a quiet card.
  • Static against dynamic energy. The same frequency sweep at fixed voltage gives each rail's C·V²·f slope.
  • DRAM activate energy, and cache hit/miss counts. Both need counters that only M-mode can program. A user-mode syscall to set event selectors would be a few lines in the worker firmware, which the lab card would need flashed.

cd build/memprobe-data
python3 ../../workloads/memprobe/gen_ops.py timer   --out .

python3 ../../workloads/memprobe/gen_ops.py decomp  --out . --lines 1500 --reps 3 --pre-delay 1000

python3 ../../workloads/memprobe/gen_ops.py refresh --out . --name refresh_jit --n 19000 --jitter 3000 --start 0x1000

for p in l1 l2 l3near l3far dram_seq dram_row; do python3 ../../workloads/memprobe/gen_ops.py table --pattern $p --out-file $p.tbl; done
python3 workloads/memprobe/run_power.py --host-bin build/memprobe/host/memprobe_host --tables build/memprobe-data --out build/memprobe-power --seconds 6 --gap 4
python3 workloads/memprobe/analyze_power.py build/memprobe-power --json summary.json
python3 workloads/memprobe/analyze.py --data docs/reports/data/2026-09-19-memprobe-aifoundry2 --out summary.json
