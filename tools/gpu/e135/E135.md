## The question

On the ET-SoC-1, zeros beat random numbers where the clock sets the pace, by how far random data's power overshoots a
limit: in a burst on a cool die the governor's power test (a ~1.3 s average of board power against 65 W) steps the
clock down, so "a kind's burst clock is set by how far its power at 800 MHz overshoots 65 W" (the kinds page, section
3; E64's cool-die ladder in `docs/reports/data/2026-10-23-e64-horace-power-limit/results.md`); sustained, the 65 °C
thermal test acts instead (E80, E83). Horace He saw zeros beat random on an A100 and put it down to the same thing, from
nvidia-smi and the literature. **Is the A100's zeros-against-random gap set the same way, measured, kind by kind?**

## What runs

**Platform.** Modal workspace `yaroslavvb` (his own; profile `yaroslavvb`), `gpu="A100-40GB"`, 2 CPU cores, 8 GiB.
Image: Modal's `debian_slim`, Python 3.11, `torch==2.5.1` (PyPI's CUDA 12.4 wheels; cuBLAS is the
`nvidia-cublas-cu12` torch pins), `nvidia-ml-py==12.560.30`, `numpy==2.1.3`. App and Volume `e135-a100-kinds`. Code:
[`e135_app.py`](e135_app.py). No secret is read or written by it.

**Two units, A and B**: two containers started together, each on its own A100. They are the independent replicates
(the unit of replication is a pass, never samples inside one window); the board is logged only as a 12-hex hash of its
UUID, so whether Modal gave two boards shows in the data. Each unit saves every step to the Volume as it ends.

**The kinds.** Built on the GPU exactly as Horace He's scripts build them ([gist `Chillee/42e4635c`](https://gist.github.com/Chillee/42e4635c59760a74cb3b4ba7ea5ad9f8):
`mm_weird.py` and `sustainable_clock_speed.py`; read 2 Nov 2026), in the format named:

| E135 name | his name | built as |
|---|---|---|
| `zeros` | zeros | `torch.zeros` |
| `randn` | randn | `torch.randn` |
| `rand` | rand | `torch.rand` (uniform in [0, 1)) |
| `twos` | twos | `torch.full(shape, 2)` |
| `pi` | all_pi | `torch.full(shape, 3.1415926535897932384626)` |
| `ternary` | ternary | `torch.randint(-1, 2, shape)` in the format |
| `onebit` | one bit | `(torch.randn(...).view(int16) & 0b1000).to(format)`: the integer 0 or 8 converted, so the values are 0.0 and 8.0, about half each (`int32` view for fp32). His post describes "only the 4th bit set"; his code makes numeric eights, and E135 follows the code |
| `checker` | checkerboard | `torch.randn` with every element where (i − j) is odd set to 0 (his `torch.where` on the two `arange`s) |
| `sparse75` | sparse (the post) | `torch.randn` with a random 75% set to 0 (mask drawn in fp32, so exactly 75% in expectation): the post's "a random 75% masked" |
| `sparse_neg` | sparse (`mm_weird.py`) | `torch.where(x < 0, 0, x)` on `torch.randn`: the negative half zeroed, as the gist's script does; used only in its protocol |
| `rand_full` | (int8 only) | `torch.randint(-128, 128)`: every int8 value equally likely, the ET-SoC-1's "random −128…127" (E80 `int8/full`) |
| `randn_q` | (int8 only) | `clamp(round(32 · randn), −128, 127)`: a quantised normal, σ = 32 steps |

int8 `zeros`, `twos` and `ternary` are the same constructions in int8. Every operand pair is `A = f(M, K)`,
`B = f(N, K).t()`, as `mm_weird.py` builds them (both operands K-contiguous), with M = N = K = 8192 except where said.
Each (format, kind, pass) draws A and B from their own seeds (a hash of the label, so A ≠ B), the same on both units.

**The formats.** bf16 and fp16 `torch.mm(A, B, out=C)`; tf32 `torch.mm` on fp32 operands with
`torch.backends.cuda.matmul.allow_tf32 = True` (off everywhere else); int8 `torch._int_mm(A, B, out=C)` into int32.
TFLOPS (TOPS for int8) count 2 n³ per call.

**A cell.** Build the operands; three warm-up calls and three timed ones size an event group (calls per CUDA event,
about 4 ms of calls, set from the measured time: expected 1 call for bf16, fp16 and tf32 and 2 for int8 at 8192³); check C (zeros must give C = 0); wait for the
GPU to cool (below); then **63 s of back-to-back calls from the idle GPU**, a CUDA event after every group, at most 4
groups queued ahead, the host time of the start event taken just before it, so the events line up with the NVML
samples. **Windows, in seconds from the first call: burst [0, 3), sustained [3, 63), late [48, 63), early [0, 0.5).**
A window's rate is (groups whose midpoint falls in it) × calls × 2 n³ ÷ their summed event time.

**NVML, every 100 ms**, in a process of its own: SM, graphics and memory clocks; `nvmlDeviceGetPowerUsage`; the total
energy counter; field values 186 (instantaneous power), 185 (1 s average power) and 82 (HBM temperature); GPU
temperature; the clock-event (throttle) reasons bitmask; the enforced power limit; the P-state; utilisation; the power
and thermal violation counters. Getters only; a getter that answers "not supported" is dropped and named in the log.
A window's power is the energy counter's slope across it where the counter reads, else the mean of the power readings.

**Cooling.** Each unit starts with 60 s idle (`idle0`); **T_idle is the lowest GPU temperature in its last 20 s**, and
every cell and protocol arm starts after at least 20 s idle **once the GPU reads ≤ T_idle + 5 °C**, or after 120 s,
when it starts anyway; the start temperature and whether the target was reached are recorded for every cell.

**Horace's protocol.** `mm_weird.py`'s loop exactly: its six kinds in its order (`randn`, `twos`, `sparse_neg`,
`onebit`, `rand`, `zeros`), `random.seed(0)` and a shuffle per iteration, 10 iterations, fresh tensors for every trial
(torch's generator continues; his script never seeds it, E135 seeds it once with 0), `torch.mm(A, B)` allocating its
output, TFLOPS from `do_bench` and the median of the 10. `do_bench` is triton 2.3's (April 2024), transcribed in
`e135_app.py`, because the image has no C compiler for triton's own driver: five calls to estimate, n_warmup and
n_repeat from 25 ms and 100 ms, the L2 flushed by zeroing 256 MB before every timed call, the mean returned. The same
loop runs over the post's nine kinds (`sparse75` for sparse) as `article9`.

**The lower cap** (unit A only, after its bf16 block). Target **330 W** (his footnote's limit) if the limit found
exceeds 340 W, else 80% of it rounded down to 10 W, never below NVML's minimum. One `nvidia-smi -i 0 -pl <target>`;
**applied** if it exits 0 and the enforced limit reads within 1 W of the target. If applied: bf16 `zeros`, `randn`,
`twos` and `rand` (the seeds of pass 1, so the very same operands) and the gist protocol at the new cap; then, in a
`finally` block, `nvidia-smi -i 0 -pl <the limit found>`, up to three tries, the power-management and enforced limits
read back; then a 13 s bf16 `randn` cell at the restored limit. If not applied it is skipped and the reason recorded.
Every step is labelled by the limit actually enforced when it starts, so a failed restore cannot pass as the default.

**The ladder** (unit B, last; exploratory, reported, not scored): bf16 `zeros` and `randn` at 4096³ and 2048³, 3 s + 30 s.

**The plans** (`plan_A`, `plan_B` in `e135_app.py`; `--mode dry` prints them):
- **A:** static reads, idle0, gist6, article9; bf16 `zeros randn twos rand pi sparse75 onebit checker ternary`; the
  lower-cap arm and the after-cap cell; bf16 `randn`, `zeros` pass 2; fp16 `zeros randn twos rand`; tf32 the same;
  int8 `zeros rand_full twos randn_q`; 30 s idle.
- **B:** static reads, idle0; bf16 in A's reverse order; article9, gist6; bf16 `zeros`, `randn` pass 2; int8, tf32 and
  fp16 each in A's reverse order; the ladder; 30 s idle.

**Budget.** `modal billing rates`, read Mon 2 Nov 2026 10:33 PST: A100-40GB $2.10/h, $0.0473 per core-hour, $0.008 per
GiB-hour, so **$2.2586 an hour per unit**. Planned (an 80 s cooling wait each): A 86 min ($3.25), B 80 min ($3.01),

**The smoke (S0), declared.** Unit `S`: the static reads, 15 s idle, bf16 `randn` at 2048³ for 2 s + 4 s, int8

## Frozen predictions

From [`predictions-e135.json`](predictions-e135.json) `predictions` (its sources are in the same file):

- **P1, Horace's numbers.** On his A100 at its 330 W limit, `mm_weird.py` (bf16, 8192³) recorded zeros 292.30 /
  randn 239.41 = **1.221** (28 Apr 2024) and 291.63 / 240.43 = **1.213** (21 Jun); the post's chart reads 236.47 (randn)
  to 287.69 (zeros) over nine kinds, **1.217**; the post's text, 295 / 257 = **1.148**, with no size or format stated
  (Q132(g) §d; Q130(e) §1). Ours is at our own unit's cap, so P6 carries the comparison.
- **P2, the ET-SoC-1 mechanism.** bf16 sustained at the default cap: random's SM clock below zeros' (≤ 0.99×), the SW
  power cap reason active in ≥ 50% of random's samples, every thermal reason (HW slowdown, SW thermal, HW thermal) in
  ≤ 5%, and random's power within 0.95–1.03 of the enforced limit.
- **P3, speed follows the clock.** Per unit, cap, format and window (burst, sustained), TFLOPS per MHz of SM clock
  agrees across kinds within 3%: the kind changes the speed only through the clock (the ET-SoC-1's "at a pinned clock
  the data never changes the speed", kinds page section 3).
- **P4, the cap's dichotomy.** Every default-cap cell, sustained: a kind below 95% of the limit holds ≥ 99% of the
  maximum SM clock with the SW power cap ≤ 10%; a kind with the SW power cap ≥ 50% sits at ≥ 95% of the limit.
- **P5, the lower cap** (if applied): random bf16 sits on the new cap (0.95–1.03 of it, SW power cap ≥ 50%); the
  zeros/random gap at the new cap is larger than at the default; and every kind whose default-cap power was under 95%
  of the new cap keeps its clock within 1%.
- **P6, his gap carried to our cap through the overshoot.** If random's power above P0 = 88 W (his idle) scales as
  clock^n with n between 1 and 3, and his zeros ran under his cap at the full clock, his 1.221 at 330 W gives
  g(L, n) = max(1, 1.221 × ((330 − 88) / (L − 88))^(1/n)) at a limit L: at 400 W, **1.000 / 1.075 / 1.122** for
  n = 1 / 2 / 3. The bf16 sustained gap (each unit's mean over its passes) falls inside [g(L, 1), g(L, 3)] at each
  unit's enforced limit. At 330 W, if the lower cap is applied there, the cells' gap and the gist protocol's both fall
  in **1.17–1.26**.
- **P7, no slow governor.** bf16: the sustained gap minus the burst gap lies in −0.01 to +0.05 for every unit and pass.
  (The ET-SoC-1's grows from ×1.14–1.15 to ×1.29–1.31, because its sustained limit is a thermal trip.)
- **P8, thermal reasons inactive.** Every cell's sustained window: each thermal reason in ≤ 5% of samples.
- **P9, the gap where and only where the cap acts.** For every unit, cap, format, pass and window (burst, sustained):
  random capped (SW power cap ≥ 50%) with zeros not (≤ 10%) gives zeros/random ≥ 1.02; neither capped (both ≤ 10%)
  gives |zeros/random − 1| ≤ 0.02.
- **P10, the chart's order.** The nine bf16 kinds' sustained TFLOPS (default cap, pass 1, mean of A and B) rank as the
  post's chart does: Spearman ρ ≥ 0.7; not applicable if they spread by less than 2%.
- **P11, his protocol reads our gap.** Per unit at the default cap, |gist6 zeros/randn − the bf16 sustained cells'
  zeros/randn (pass 1)| ≤ 0.03.

## Rules, which can fail

[`reduce_e135.py`](reduce_e135.py) scores **R1–R10** on units A and B (`R1` = P2, `R2` = P3, `R3` = P4, `R4` = P9,
`R5` = P5, `R6` = P6, `R7` = P7, `R8` = P8, `R9` = P10, `R10` = P11; P1 is the comparison P6 carries). R1 is
scored per replicate (unit × pass): **HOLDS** if every replicate meets it, **FAILS** if none does, **MIXED** otherwise.
Every other rule needs every applicable item to meet it: **HOLDS** or **FAILS**, and **N/A** where nothing applies
(R5 when the lower cap could not be set). Thresholds are `thresholds` in the predictions file. The reducer's checks
(the GPU is an A100, zeros give C = 0, ≥ 90% of the expected samples in each sustained window, every cooling wait)
are printed beside them, not scored. [`selftest_e135.py`](selftest_e135.py) shows every rule holding and failing on
made-up units ([`selftest.txt`](selftest.txt)).

Reported beside the rules, not scored: every cell's rate, clocks, power (and pJ per FLOP), temperatures and reasons
per window; the gaps with each replicate, mean, range and a t-interval where n ≥ 2; the early window's clocks (how fast
the power controller acts); the ladder; and the comparison with the ET-SoC-1's gaps (`etsoc1` in the predictions file:
fp32 ×1.142–1.149 burst and ×1.293–1.306 sustained, fp16 ×1.119–1.129 and ×1.297–1.316, int8 ×1.00 and ×0.99–1.03,
from E80's and E83's `results.json`).

## What this does not do

- It sets nothing on the GPU but the one power limit of the lower-cap arm, and only if the container may: no clock
  locks, no application clocks, no persistence, ECC or compute-mode change.
- It touches no lab card and posts nothing in `#community-lab`.
- It is not Horace He's unit: his ran at a 330 W limit; Modal decides ours, its variant (SXM4 or PCIe) and its cooling.
- It tests one shape family (square, 8192³, both operands K-contiguous) and, exploratory, two smaller sizes.
