## The question

1. **fp16's rest.** In fp32, on zero products with B's random signs, a tile held within each op at a walking tile's op-end sums (`b_B_z`) carries 0.97 ± 0.01 (card 1) and 0.95 ± 0.04 (aifoundry3) of B's rest, `b_B_w` − `z_s`. fp16 has never had that design. E128 ports it as it is (`fp16.b_B_z`, `fp16.b_B_w` on E104's `fp16.z_s` B stream), so fp16's rest is located the same way, beside the step and its zero-product held share in the same session.
2. **The part that goes with the sums changing.** E108's three tiles alternate between adding and subtracting different numbers of times an op (`z_s` 2,268, `b_B_z` 1,800, `b_B_w` 2,016), so `b_B_w` − `b_B_z` (0.09 ± 0.04 W) was a tile contrast, and how much of the rest goes with the sums changing was read only with the alternations priced post hoc (R12 0.68–1.05). E128 builds a triple whose eff_sub sequences are identical micro-op for micro-op: **`z_s` itself, `b_B_zm` (held) and `b_B_wm` (walking)**, in both formats. Then `b_B_zm` − `z_s` is the accumulators differing, `b_B_wm` − `b_B_zm` the sums changing, with no difference in alternations, and their shares of `b_B_wm` − `z_s` need no pricing.
3. **The moving-sum ratio** (E104-R6, E108-R10, E122-R10): fp16's walking alternation premium over fp32's, a third session, scored against card 1's session (E108) and aifoundry3's (E122) at E82's per-type card scale, and pooled over the three sessions' kept passes.

## The tiles

[`make_e128.py`](make_e128.py) writes them, with every expected accumulator from `accum.c` (the RTL's arithmetic), the manual's sentence and fl(n S): on all 20 tiles at every length the three coincide, so a read-back miss means a tile is not what it is called. A lane's eff_sub on a micro-op is sign(C) xor sign(a) xor sign(b) (fp16: one per product). In `z_s` (A = −0 at k ≥ 1, E88's random ±1 B, k = 0 (2^50, 2^50), C = n 2^100 > 0) it is NOT sign(b) at k ≥ 1 and 0 at k = 0. The matched tiles keep `z_s`'s B stream at k ≥ 1, keep sign(a) = 1 at k ≥ 1 (−0 held, −1 walking) and keep C > 0 in every column, so their eff_sub sequences are `z_s`'s.

Every function on every path below is the same at both ends of the line; the dispatcher gained one case on the line (FRU commands, not sent here). The ids of the nine commands sent, and of the firmware-revisions query, the statistics reset and the log-level set, are the same in all 13 revisions of the public `device_mgmt_api_spec.h` and in the box's own header, the one the lab's `ettelem` was built against (`/opt/et/.../device_mgmt_api_spec.h`, sha256 `699a4ecc…`; `desk/dmcmd-ids-e128.py`, `desk/box-tools.txt`). The lab's `ettelem` binary on the box (sha256 `8008f96f…`, built 25 Sep 15:14) carries the usage string of `tools/ettelem/ettelem.cpp` at `de262730`–`eb7c762d` (comment changes only between them), so the commands are those of that source. WRITE means anything more. **The run sends no WRITE.**

Where the samples come from: the 10 Hz sampler through every pass (`ettelem sample --seconds <s> --every-ms 100`), and `lib.sh`'s `die_c` at both ends of every block (`ettelem sample --seconds 1 --every-ms 500`, two samples). **Side effects on the path, read off the source, none a WRITE as defined above:** an I2C read issues the register's address in the bus's write phase (`IC_DATA_CMD`), then reads; no PMIC register's content is written. If a read fails, the firmware soft-resets its own I2C controller and retries (`get_pmic_reg` → `i2c_soft_reset`): an error path of the SP's own bus controller, not the PMIC and not the card, in every run since September. A PVT voltage sample with a fault marks that shire's sensor bad in RAM (`pvt_bad_min_shire_mask`, an error path). Every handler writes its response into the SP's completion queue and lines into the SP's log buffer.

**Not sent, and how that is enforced.** Every telemetry call in E128's blocks goes through `ettelem_guard.sh`, an allow-list that passes only `ettelem config` and `ettelem sample --seconds <n> --every-ms <n>` and refuses everything else (exit 97) before the device is opened: so **not** `DM_CMD_SET_STATS_RUN_CONTROL` (62, `sample --reset-ms`, the statistics reset: allowed by the owner's ruling of 31 Oct, but not needed here and not sent), **not** `DM_CMD_SET_DM_TRACE_CONFIG` (67, `loglevel`), **not** the trace-buffer read (`sptrace`). `lib.sh`'s `drain_mgmt`, which runs the vendor tool `dev_mngt_service` after a sampler fails to start or ignores SIGTERM, is replaced in E128's blocks by a refusal: the vendor tool is never run, and a sampler that will not start fails the block instead. Nothing in the run sends `DM_CMD_GET_MODULE_FIRMWARE_REVISIONS` (14, which writes the PMIC's firmware-management register), a raw residency read of state 4, or any set (`DM_CMD_SET_MODULE_STATIC_TDP_LEVEL` 26, `DM_CMD_SET_MODULE_TEMPERATURE_THRESHOLDS` 22, or any other). `selftest_e128.py` checks the guard's refusals against a stub reader, on the Intel; the guard is never tried on the box.

**The workload's own commands (the ops node, not device management).** `build/sparsity/host/sparsity_host` (the power runs and the heater) and E104's read-back host open only the ops node (`createPcieDeviceLayer(true, false)`, `workloads/sparsity/host/main.cpp` and `build/e104/src/host/main.cpp` on the box, sha256 `0f53a7d5…` and `bf5435ac…`), so they cannot send a device-management command. **Host-side only.** `et-lab-manifest` (sysfs and files; it never opens `/dev/et*`; the box's copy equals `tools/lab/et-lab-manifest`, sha256 `6fbb4e10…`), `et-holders` and `et-who` (`fuser`, which stats the nodes and never opens them; the box's copies equal the repository's), `flock` on `/run/lock/etsoc-shire1.lock`.
