**The pins the kit gates on:** the kernel ELF `aace138caf8071cc7679134211045a89fb09b65cc9a170bfe33409fd36b4fda0` (E136's build record; aifoundry2's
and aifoundry1's builds byte-identical, E190's kit) and its `.text` `61315bf6a449c2823fbffc33834b4c0a68aa19e8436a29c1124b15c04114b763`. Arm A builds on
aifoundry3, whose RISC-V GCC prints `(g1b306039a) 15.1.0` where aifoundry1's prints `() 15.1.0`; the string lands in the ELF, so arm A's kernel is
gated on its `.text` (E191's kit fix) and the host on its behaviour (E190's four refusals). aifoundry3 has never built rgm136 for its card.

**Three parts of the binary are used.** (1) `gemmL<MB>x<NB>x<KB>` (`SP_GEMM_LARGE`): C (MB x NB blocks of 1,024 x 512) = A (MB x KB blocks) x B
(KB x NB blocks), each block the vendor pattern's 64 x 32 x 32 tiles; every minion owns two row tiles and one column tile of every C block, loads A
with its neighbourhood (8 minions) and B with its position across the shire's 4 neighbourhoods, runs each C tile's whole K (KB x 32 ops) before its
one TensorStore, and walks the C blocks mb outer, nb inner. M is a multiple of 1,024, N of 512, K of 512 (fp32), 1,024 (fp16) or 2,048 (int8). Ops a
minion a GEMM: MB x NB x 2 x KB x 32. (2) The line-cost law's own arms `gemmc1`, `gemmc8s`, `gemmc16s` (run_gemm, unchanged since rgm107: one block;
8 blocks with C shared; 16 blocks with C shared), so each card's law constants come from the same build. (3) **Shire subsets** (`--shires <mask>
--per-shire 32`; the host refuses a GEMM with fewer than 32 minions a shire): shire s computes rows 128 (s >> 2) .. +128 and columns 128 (s & 3) ..
+128 of every C block, so `0x1` computes a 128 x 128 piece of each block on 32 minions, `0xf` 128 x 512, `0xff` 256 x 512, `0x11111111` 1,024 x
128, `0xffff` 512 x 512. Each minion's work is the full-chip GEMM's; the GEMM, its footprint in the L3 and the minions sharing the L3 and DRAM
shrink. The host checks only participating minions' tiles of C, so every subset point is checked.

**The data** (E136's own `--values` strings, `--seed 1`): random (`randn`; fp32 normal(0, 1), fp16 the same rounded to half, int8 uniform -128..127 from
`int8/full.bin`), zeros (`tiles` of the format's `zeros.bin`), `sparse50`, and real tensors (`tiles` of E101's four real tiles a format, cycled:
fp32 gpt2_l9_attn_qk, gpt2_l3_mlp_down, bert_l6_up, vit_l5_down; fp16 gpt2_l9_attn_qk, bert_l6_up, vit_l5_down, gpt2_l6_mlp_down_fp16fwd; int8
gpt2_l6_down_p999, gpt2_l6_down_p9999, gpt2_l6_down_per_token, gpt2_l11_down_p999). Each point's exact argv is in `points-e206.json` › `host_args`.

**The operations a matmul contains**, as this kernel runs them: tensor multiply-adds (4,096 MACs an op in fp32, 8,192 in fp16, 16,384 in int8),
loads of A and B tiles (an op asks 64 A lines and 128 B lines; where they come from is the line count of section 4), and one TensorStore of C per C
tile row (every 32 ops at KB 1; every 1,024 at KB 32). **No epilogue** (bias, activation, requantization) exists in it.

## 7. The scoring (`score_e206.py`; a point with no run is NO DATA, never a failure)

**The order.** Per arm (`points-e206.json` › `order`): the smoke (30 s at rest; one checked 2 s process each of p001, p046 and p021: rc 0, every

## 8. What E206 cannot say (stated before the data)

- **Sizes below the grid come only from shire subsets**, which keep each minion's full-chip work: a library that spreads a small GEMM over the whole
  chip, a batch of small GEMMs and a GEMV are not measured. A size-free small-GEMM arm needs a new kernel (a later design).
- **No epilogue**: rgm136 stores C and ends (int8 in int32); bias, activation and requantization need a kernel change and their own registration.
- **One clock** (600 MHz on both arms), no voltage ladder; aifoundry2's governed card is not an arm of E206.
- **No transistor switch is measured** (no card can). Each data kind at a fixed shape and time is a switching contrast a switch term must explain;
  a matmul model's switch definition is applied to E206's points by count, outside this registration.
- **A small GEMM's joules are a warm, repeated GEMM's**: a launch runs the same A and B for many passes (the host's 0.5 s launches), so a footprint
  the L3 holds is served from it after the first pass. **Real tensors** are four tiles a format, cycled.
- **The meter's absolute scale**: one fixed gain per board, never set beside an outside meter.
- **One session per arm, two runs a point**; no interval between sessions (E146's replicate of E136 is the lab's only spread between sessions on
  a GEMM: 0.2-0.4% in seconds, +-0.6% in W over idle, one card).
- **Arm B may not run** (section 6); if it does not, E206 says nothing about card 1.
- **The one-shire points barely rise above idle** (added before any datum, A1): p094, p095, p106 and p107 are forecast at 0.19-1.09 W over idle
  by F1, P0 and F2 on either arm, against a card at rest of 23.2 W (A) and 29.2 W (B), and the three models agree there within about 0.3 W. S2's
  10% is 0.02-0.11 W and S3's 5% is mostly the rest reading, so at those points S2 and S3 mostly test the meter's noise; they count as
  registered (no point is dropped).
- **The cycles are the kernel's counter**, not a simulator's; F1's seconds and cycles are one law (wall-based anchors). On E190's 8,192^3 fp32
  GEMM on card 1 the two agreed within 0.3%: the smoke's counter read 1,451.2 cycles an op, the bursts' mean 0.31774 s a GEMM is 1,454.5 at 600 MHz.
- **Not the vendor's binary**, not a library GEMM: the vendor pattern built from public sources (E136).
