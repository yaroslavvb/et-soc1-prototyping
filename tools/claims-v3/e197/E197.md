## 1. The question (quoted from the proposal, section 1)

On every minion, one hart, streams of register-to-register scalar integer instructions with no load, no store and no branch in the
timed body, in pairs of kinds that run the same instruction count at the same issue rate and differ in one thing. What does the
scalar register file cost, per event, in pJ and in electrons through the core rail and through the 12 V input:

1. **a stored bit that changes on a write** (a register-file cell), with the source, port and result streams, and how often each
   encoding bit changes, held identical between the two kinds;
2. **a result bit along the result path into the register file**, with the sources fixed (no read-port bit changes);
3. **one register write**, against the same instruction writing x0;
4. **the destination changing** between neighbouring instructions (two destinations against one; in the second sitting, eight
   against two);
5. **a read-port bit**: on port 2 when the register is only named by bits 24:20 of an immediate instruction and no operand uses it,
   on port 1 when it is only named by bits 19:15 of an upper-immediate instruction, and on port 2 when the register is the operand of
   an `and` whose result is held at zero by the other source being x0 (does this core read the register file before it decodes, for
   instructions that use no register operand, and what does it cost?);
6. **a held one** in the two registers named in turn, when nothing at the port changes (both hold all ones, against both zero);
7. **a bit of the read field**: the second source field changing in 1, 3 or 5 bits (zero contents: a 0, 1, 3, 5 ladder), and, in the
   second sitting, eight source registers in turn against two.

What is new (the proposal's words, shortened): no scalar register-file ladder has run on a card. E60 and E61 priced the vector unit's
read port and result bits, E74 the vector register file's cell, the energy catalogue the scalar instructions on zeros, a constant and
random data (its sinks are rewritten with the value they already hold, so no scalar cell flips there), and E192 (the lab's
registration of request `1113-x01-intbits`) flipped operand and result bits with one destination, so that its result bits and its
destination's cells change together.

## 2. The kinds and the trains (registered; request.md section 2, `make_images.py` and `trains.tsv`, checked cell by cell in section 17)

**Forms, images, kinds** (quoted, with the code's reading). A form is one loop body of 128 instructions, all 32-bit encodings, its
head 64-byte aligned; an image is the values of the registers the form names; a kind is a (form, image) pair, `form.image`. Every
kind of one form runs byte-identical code. Sources are never written, sinks never read. Seventeen forms (request.md's table):
`rot` (`mv d_i, s_i` for i = 0..7, then `mv d_(i+3 mod 8), s_i`: each sink receives s_m and s_(m-3) in turn) and `rot2` (the second
half `mv d_(i+2 mod 8), s_i`), with s = x18..x25 and d = x11, x12, x9, x15, x30, x14, x6, x8, chosen so that the destination field
changes in the same bits, position by position, between instructions 1, 2, 4 and 8 apart in both forms; `res` (`and x5, x18, x19 ;
or x6, x18, x19`), `resf` (the same into x5 alone), `resz` (into x0); `rd2i` (`andi x5, x0, 21 ; andi x5, x0, 26`: bits 24:20 name
x21 and x26, no operand used), `rd2r` (`and x5, x0, x21 ; and x5, x0, x26`), `rd1u` (`lui x5, 168 ; lui x5, 208`: bits 19:15 name x21
and x26); `idx0`, `idx1`, `idx3`, `idx5` (`and x5, x0, x22` with x23, x24 or x9 in turn: the second source field changes in 0, 1, 3, 5
bits); `rn8` (`and x5, x0, p` over x16, x17, x19, x18, x26, x27, x25, x24); `wn1`, `wn2`, `wn8` (`and d, x0, x0` over one, two or the
same eight destinations); `nop`. **The loop frame:** after the body every loop has the same words, `addi x10, x10, 1 ; csrr x13,
hpmcounter3 ; bltu x13, x28, head` (131 instructions an iteration), then 29 copies of `addi x28, x28, 2` that run once, at the loop's
end, so the 64-byte block holding the branch and the block after it are the same bytes in every form (words `00150513 c03026f3
dfc6ece3` and `002e0e13`). **Images:** M is a fixed 64-bit word with 32 ones (seeded), M32 a second one 32 bits from M; `x64` (the
sources alternate M and ~M: every `rot` write changes all 64 cells of its sink, every `rot2` write none), `x0` (every source M),
`k0`, `k32`, `k64` (a = M and b = M, M32 or ~M), `d64` (x21 = M, x26 = ~M), `e0`, `e32`, `e64` (both 0, both M, both all ones), `z`
(every named register 0). Every kind's register values and designed counts are in [`desk/host-list-e197.jsonl`](desk/host-list-e197.jsonl),
the built host's own table. **Designed counts** (per body instruction, steady state, the previous instruction taken cyclically):
`f1`, `f2` the bits that change in the registers named by bits 19:15 and 24:20; `a1`, `a2` the same where the instruction uses that
operand; `res` the result's changed bits; `cell` the destination's stored bits that change; `i1`, `i2`, `iw` the changed bits of the
two source fields and the destination field; `enc` the changed encoding bits; `h1`, `h2` the ones held in the two named registers;
`writes` the register writes.

**The trains.** A train is a number of device processes back to back; each process is 13 launches of 0.4 s (launch 0 settles; then
three quads, S F F S or F S S F, the orientation alternating process to process from the train's first), and every quad reads D(F) -
D(S): the train form of E182 and E183. **Each train's control is its own S kind, in the same device process.** The designed changes
below are the host's own table, F minus S, and equal request.md's cells, train by train (section 17; `enc` follows from the field
counts and equals their sum):

## 3. Cores, harts, card, clock (registered)

- **All 32 shires x 32 minions, hart 0 of each**: 1,024 instruction streams, one a pipeline (a second hart would interleave two
  streams and lose the designed neighbours); hart 1 of every minion returns to the firmware at once. The loop reads `hpmcounter3`
  once an iteration; each launch reports the fewest iterations of any hart (quoted).
- **aifoundry3 card 0** (the proposal's "lab host 3, card 0"; request.md section 10 lets the operator put the lab's host name back),
  **as found: 600 MHz, pinned by its zero TDP** (`docs/findings/14-card-behaviour.md`), mesh 400 MHz; the lock
  `/run/lock/etsoc-shire0.lock`. **Nothing is set:** no change of voltage, frequency, firmware, governor, TDP, threshold or fan; no
  reset, no power cycle, no privileged access.
- **One card only** (quoted, *desk check of code:* `host/main.cpp` `checkOneCard()`, `run_session.sh` lines 73-90): before opening
  anything the host and the session count the card nodes (`/dev/et<N>_ops`); with several, `ET_DEVICES` must name one and every
  binary run must read it; after opening, the runtime must list exactly one device. aifoundry3 has one card.
- **Reads only:** every device command the session's chain sends (the host's, the sampler's, `et-who`'s) is classified by the kit's
  device-command audit before the card day (`dmcmd_audit` GO, every send site READ). No statistics reset, no firmware-revisions
  query, no set of any kind.
- aifoundry3 is the lab's card for switching power over idle, never absolute watts (14-card-behaviour.md, the card table): E197's
  prices are differences inside a train and anchors over idle.

## 4. What is measured, and how (registered; request.md sections 4 and 6)

- **One sampler at 10 Hz for the whole session**, started first and stopped with SIGTERM only, at the end: board power (`board_w`,
  the 12 V input), the minion rail's power and voltage (`sp.minion_w[0]`, `sp.minion_mv[0]`), the die reading
  (`temp_c.minshire[0]`) and the minion clock (`mhz.minion`). Request.md prefers the lab's per-sensor sampler on this card, the plain
  one the fallback, and leaves the choice to the lab. **The lab's choice:** the plain sampler (`ettelem sample --every-ms 100`, no
  statistics reset), unless the kit's device-command audit reads the per-sensor sampler's command as a READ, as E192's kit did, and the
  kit chooses it in a dated kit note before any datum. Either way the reduction reads only the fields above (*desk check of code:*
  `reduce_regfile.py` reads `board_w`, `mhz.minion`, `sp.minion_mv[0]` and `sp.minion_w[0]`; the live stops read
  `temp_c.minshire[0]`), which both samplers give. Which sampler ran is recorded with the data.
- **A train process**: one device process, `timeout 10 regfile_host --train F,S --orient SFFS|FSSF --launches 13 --window
  240000000 --stop-file OUT/STOP` (`timeout 10`, not the proposal's `timeout -k 1 10`: departure D1, section 15): 13 launches of
  240,000,000 cycles (0.4 s at 600 MHz); launch 0 settles with the orientation's first letter and launch n >= 1 takes letter (n - 1)
  mod 4, F the first kind, so the quads 1-4, 5-8 and 9-12 each read D(F) - D(S). **An anchor**: `timeout 10 regfile_host --kind K
  --seconds 3 --window 240000000 --stop-file OUT/STOP` (1 s in the smoke). The host starts no launch that could not end inside its
  8.5 s budget (at the slowest clock it allows for, 500 MHz, plus 1 s), in every mode, and none once the stop file exists.
- **Every launch prints one `REGFILE {json}` line:** the kind and its designed counts, the launch index and its letter, the loop
  iterations (their sum over the harts, and the fewest and most of any hart), the body instructions, the neighbourhood counters read
  before and after the loop (thread-0 instructions retired, `hpmcounter4`; I-cache requests and misses, `hpmcounter7` and `8`; L1
  data misses, `hpmcounter6`), the cycles (`hpmcounter3`), x1 and x3, the deadline, the launch's epoch bounds, the participant count
  and `check_bad` (the harts whose written registers do not hold, after the loop, the values the kind's model gives).
- **Rate and energy** (quoted): R = the train's median device rate (body instructions a second over all harts); energy an
  instruction = D / R; electrons through the 12 V input E / (e x 12 V) (the input's voltage is not metered: 12 V nominal); through
  the core rail E_rail / (e x V_rail), with the anchors' measured rail share and the rail's measured voltage. The card's issue rate
  for this loop is measured per launch; the proposal sizes it at 4.5 to 5.6 x 10^11 a second.
- **No heater:** inside a train two kinds alternate launch by launch from one thermal state (quoted).

## 5. The run: the session, its blocks and their order, the smoke (registered; request.md sections 2, 4 and 8, `run_session.sh`)

- **The session is the proposal's reference session**: `run_session.sh` with `stopwatch.py`, `trains.tsv` and the lab's runner
  `lab/run_trains.py` in place of `src/run_trains.py` (section 15), driven by the kit with the box's tools (the form E193's kit used
  for its proposal's runner). A kit port is allowed only if the kit shows it equal on every point of this section and sections 4 and 9
  (BUILD.md: "the lab session's own kit ... is meant to run the same trains in the same order").
- **Before anything opens a card node:** one card (the node count); the card free (`et-who --check` exits 0, no other user's device
  process runs, and a probe of the card lock succeeds: the existing lock file opened read-only, `flock -n`, never created, never waited
  for); a fresh OUT (a folder holding any file of an earlier session is refused, exit 2). Otherwise nothing is opened (exit 3).
- **Then** the one sampler, the stopwatch, 10 s, the holder check again (every holder must be this session's own sampler on this card's
  nodes; no other user's device process), and **the smoke block** under the card lock: 5 s idle; `nop.z`, `res.k0` and `res.k64` as
  1 s bursts, each after 4.5 s idle; two train processes of T8's kinds, one of each orientation, labelled `smoke` (never a train);
  then the gate: both processes 13 launches, every launch ok with its letter as planned, every launch's rate within 3 % of the others'.
  A failed gate ends the session before any train block (exit 7).
- **Then the blocks**, each under the card lock (the lock file on fd 9, `flock -n`, never waited for, exit 75 if busy; every device
  process of the block keeps fd 9 open, and the lock is released by closing it, never by an explicit unlock, so it lasts while any of
  them runs). The smoke block and the first block run back to back (the lock free only while the holder check is made); between two
  blocks the lock is released for 30 s; the holder check is made again before every block, and a holder stops the session.
- **A block:** 10 s idle (marked `before`); the anchors `nop.z`, `res.k0`, `res.k64`, each a 3 s burst after 4.5 s of idle
