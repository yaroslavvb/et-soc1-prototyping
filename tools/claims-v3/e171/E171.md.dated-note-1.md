## N1. P8-KA pooled reads only E171's and E172's own scored sessions (the verifier's fault 1)

**What was wrong.** E171.md names the pooled read as `score_p8_600.py ka-pooled <E171 scored.json> <E172 scored.json>`. That function
reads any two files. The verifier fed it E171's scored session twice and it read PASS, n 4; E172's twice, and the pair swapped, read the
same. It checks no run, card, predictions file or scorer. The runbook's `ka` route passes the right pair, so the card-day path was safe;
a call by hand, or a copied file, was not.

**Registered now.** The pooled reading is the one `tools/claims-v3/p8-600/score_p8_600_v2.py ka-pooled <E171 scored.json> <E172
scored.json>` gives (the next commit), and no other. It refuses, with exit 6 and nothing written, unless every one of these holds:
1. the first file's `run` is `E171` and its `card` is `aifoundry3`; the second's `run` is `E172` and its `card` is `aifoundry1c1`
   (the registered order of the two arguments);
2. each file's `predictions` is its card's frozen file, `tools/claims-v3/kinds/blind8/predictions-pool8-<card>.json`, and its
   `predictions_sha256` is that file's line in Q142(x)'s `SHA256SUMS` (aifoundry3 `d68ff9f1e057…`, card 1 `1e55ac1ace1c…`);
3. each file's `scorer_sha256` is the committed scorer's, `cd5b602484d7…` (`tools/claims-v3/p8-600/SHA256SUMS`, `a518aa11`), and the
   scorer on disk still has it;
4. each was scored through the C gate: its `c_sessions.ok` is true;
5. the two are different files with different contents;
6. each file's rows are its own card's: every scored row's a-priori D equals its rate times that card's frozen per-op coefficient
   (`M10.k_J_per_op` in the card's predictions file), within 1e-9 W, and both check anchors have a row. A file copied from one card and
   relabelled as the other fails here.

Then it calls the committed `ka_pooled` on the two files, unchanged: the test, the minimum of 4 and the NOT SCORED cases are E171.md's.
The committed `score_p8_600.py ka-pooled` stays in the tree as committed; its output is not the registered pooled reading. The runbook's
`ka` route calls v2 (`tools/claims-v3/q141k-runbook/k6/s22_collect_k6_v2.sh`, two commits later).

## N2. The record names each scale anchor's C status, and an arm reports s without any whose C is not all PASS (the verifier's fault 2)

**What was unstated.** P8-KC removes a pool-8 tile whose C is not all PASS from every scored set (POOL8-REGISTRATION § 7). A scale
anchor is an input to s, not a member of a scored set. So a pool-8 scale anchor whose launches failed C would still set s, and through s
every float primary, A1 and KA, while P8-KC listed it as excluded. E78's `fp32.randn` and `fp16.randn`, the other inputs of s, are
outside P8-KC altogether: it covers pool-8 tiles only. The verifier showed both on synthetic sessions on both cards. This matches the
registration's words, but no file said it.

**Registered now, before any data.**
- **The primary is unchanged.** s is as POOL8-REGISTRATION § 3 and E171.md register it: every scale anchor the session ran and the
  primary reduction holds enters s, whatever its C status. Every registered verdict is read from the committed scorer's `scored.json`.
- **The record names each scale anchor's C status.** After the collector, `score_p8_600_v2.py scale-c` (the next commit) writes
  `scale-c.json` and `scale-c.md` beside `scored.json`. From the same check of C the scorer read, and by P8-KC's own rule (E163's
  `c_status`, as the committed scorer copies it: every launch record of the item in a kept pass's `runs.jsonl` has a C record judged
  PASS), they give the C status of every anchor that can enter s: pool 8's four float scale anchors, and M10's own list, of which E78's
  `fp32.randn` and `fp16.randn` run in this session. Reported only, beside them: E78's other four items and the tie (`fp32.zeros`,
  `fp16.zeros`, `int8.zeros`, `int8.full`, `anchor_pi`), on which the reduction's footing rests.
- **The arm `c_clean_scale`, reported beside, never the verdict.** If an anchor that entered s is not all PASS, s is read again by the
  frozen `predict_pool8.scale` from a copy of the primary reduction without those anchors' items. Every rule is scored on that copy by the
  committed `score_reduction`, with the same C status and scored sets. The record gives its s, its verdicts, the rules whose verdicts
  differ from the primary's, and its P8-KA block, which the pooled read reports beside (`ka-pooled --scale-c`). If every anchor that
  entered s is all PASS, the arm is the primary and is not recomputed; the record says so. If no anchor is left, the arm's s is 1
  (M10's rule when no anchor is measured) and its KA reads NOT SCORED.
- **How the records read it.** A difference between the arm and the primary is reported next to the registered verdict and never
  replaces it. An E78 footing item whose C is not all PASS is named for the records; no arm re-reduces the session, because no such
  reduction is registered.
- **Refusals.** `scale-c` refuses, with exit 6 and nothing written, a `scored.json` that is not this run's (run, card); that was not
  scored on this reduction (`reduction_sha256`), on these predictions (`predictions_sha256`) or by the committed scorer; that was not
  C-gated; whose P8-KC block differs from the one this check of C gives; or whose scale differs from the one the frozen `scale` gives on
  this reduction. The frozen inputs' refusals are the committed scorer's (N3).

of them, so the refusal holds. The records quote "non-zero (1 or 9), nothing written". No code changes; v2 keeps the same codes and adds
