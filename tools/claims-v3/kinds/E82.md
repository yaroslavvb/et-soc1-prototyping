# E82: the kinds-of-numbers energy matrix replicated on aifoundry1 card 1 (Q130, 600 MHz)

*Pre-registered Sat 31 Oct 2026 (week 44), on the Intel, before the Discord claim of card 1, before the first launch,
and before this lane opened any E78 data. The frozen numbers are in [`predictions-e82.json`](predictions-e82.json),
written by [`make_predictions_e82.py`](make_predictions_e82.py) and committed with this file. Any change after this
commit goes in the Amendments section at the end, dated, before the data it touches; no band moves. Card:
**aifoundry1 card 1 only** (`V3_DEVICE=1`, `etsoc-shire1.lock`), 600 MHz in every sample since 25 Sep, ~499 mV, TDP 65
W, threshold 65 °C; firmware 1.2.0 (BL2 0.18.0) as last read. E82 writes no knob.*

**The question.** E78 (aifoundry3, registration `cfd94285`, amendment A1 `09c6e29b`) measures switching power and
energy per operation for 51 kinds of numbers in three formats on one card. Is that matrix a property of the chip, or
of one card? E82 runs **the same 51 tiles, the same protocol, the same code and the same analysis** on a second card
of the same chip, and asks two things: do E78's registered rules (the frozen models' rank and accuracy, the nine
mechanism tests) come out the same on card 1, and is card 1's matrix aifoundry3's up to one card-to-card scale inside
the band the two cards showed in September?

## Protocol, analysis, gates

**E78.md's, unchanged** — launch reading, quiet rule, 4 s runs, power window `[t0+1, t0+3)`, idle bracket, run gates
(600 MHz, ±3 mV, launch at 58 °C, records ok, cycles per op within 0.5% of 546 / 546 / 318, ≥ 15 samples, duty ≥ 0.97,
the dumped tile equal to kinds.json's), pass gates (> 2 failed runs, zeros line 0.25 W, zeros range 0.60 W, pi drift
0.60 W, random range 1.0 W), the per-pass interpolation of each type's three zeros, D, D32, S, the rail, pJ per op /
MAC / flop, ΔT, the pass as the unit of replication, a quantity with fewer than 3 kept passes unresolved. Read E78.md,
"Protocol" and "Pre-registered analysis".

## Decision rules

**E78's rules, scored on card 1** by `score_e78.py`'s own code with `predictions-e82.json` (rule ids kept as E78's):
R1 rank (Spearman ≥ 0.80 within each type, Q130(c) A1's out-of-sample kinds; Q130(b) r2 A and B beside), R2 accuracy
(rms ≤ 2.0 / 2.0 / 1.0 W), R3a–i (the mechanism tests, E78's thresholds), R4 (card 1's targets, above), R5 (checks,
reported); Q130(c) C-R1, C-R2, C-R3, C-R4, C-R6 and C-R9 as its README and A1 say; Q130(b) r2 in watts above fp32
zeros. **Q130(c) predicts aifoundry3** (`switching_w_600mhz_a3`): E82 scores it unchanged on card 1, and reports beside
it, as a labelled secondary that is not a rule, R2 with the predictions divided by 0.935 (the middle of the card band
below). Fewer than four kept E82 passes: every verdict NOT SCORED.

**E82's cross-card rules**, against E78's committed reduction (`docs/reports/data/2026-10-31-e78-kinds-energy-matrix/
e78.json`), on D, each kind's switching over its own type's zeros. A kind enters only if it is resolved (≥ 3 kept
passes) on both cards; both experiments need ≥ 4 kept passes.

| | rule | threshold | why this value, before the data |
|---|---|---|---|
| **X1** rank | Spearman ρ of D(card 1) against D(aifoundry3) within each type, over every kind but the type's zeros (17 / 16 / 15) | **ρ ≥ 0.90 in each type** | the orchestrator's form. Simulated with Q130(c)'s predictions as the truth, one card scale and E67's per-pass noise, it passes with probability 1.00 even at doubled noise or a 5% per-kind deviation ([7]): a necessary check that the matrix has the same shape, not a sharp one |
| **X2a** one scale, strict | the ratio of means D(aifoundry3)/D(card 1) inside **[0.88, 0.99]** for ≥ 80% of the 32 eligible kinds (frozen Q130(c) prediction ≥ 5.0 W: 14 fp32, 12 fp16, 6 int8) | **≥ 80%** | the orchestrator's form. The band: aifoundry3 over card 1 read 0.887 in September's registered values and 0.955–0.965 at the launch temperatures (note C2), per pattern 0.897–0.915 ([2]). **Its power is low except mid-band:** 0.97–1.00 for a true scale of 0.935–0.96 at E67's noise, 0.01–0.05 at 0.887 or 0.985, 0.16 at doubled noise, 0.75 with a 2% per-kind deviation ([7]) |
| **X2b** one scale, noise-aware | the ratio's 95% interval (delta method from the two cards' intervals) overlaps the band, for ≥ 80% of the same kinds | **≥ 80%** | passes for any true scale in [0.887, 1.00] and fails at 1.05 ([7]). Reported beside X2a; neither stands in for the other |
| **X3** the card scale | the median ratio over the eligible kinds | **inside [0.88, 0.99]** | 0.86–1.00 for a true scale in [0.887, 0.985]; 0.00–0.01 at 0.85, 1.00, 1.05 ([7]) |

Every cross-card rule is scored at the primary leakage slope on both cards, and its verdict at three registered arm
pairs is reported beside: each card's own idle slope (card 1 0.545, aifoundry3 0.3803), 0.3803 on both, and none on
both. A verdict that moves between arms is slope-sensitive. Also reported: each type's zero-data level S(zeros), the
idle level, the voltages, the auto slopes, per-type X2/X3 statistics, and which of E78's rule verdicts agree on the two
cards. **If E78's data are not committed when E82's are, the cross-card rules are scored in a dated addendum** by the
same code (`collect_e82.sh`, `E78DIR=`), before this lane returns.

**Failures are reported as failures**, with the measured value beside the band. No band moves after this commit.

## Card budget

**At most 90 card-minutes, ending by 19:30 PDT**: E78's budget rule in `queue_e78.sh`, unchanged (a full pass only if it
ends inside 85 card-minutes of the queue's start and before 19:15 PDT; below four passes a tier-1-only pass inside 88).
Card 1 starts 6 °C below the launch band, so a pass may take longer than aifoundry3's ~10.7 min and the rule may stop
at 4 or 5 passes. The claim is posted for the budget plus a margin, as CONTEXT §4 says.

## How to run it (for this lane)

On the Intel, after this commit is on origin/main: `rsync -a --exclude __pycache__ tools/claims-v3/kinds/
aifoundry1:nekko/tools/claims-v3/kinds/`. On aifoundry1, from `~/nekko`:

```bash
bash tools/claims-v3/kinds/run_e82.sh setup      # no device access: lib.sh and the reused files against the freeze,
                                                 # 51 tiles, the binary's strings, the plan, a V3_DRY pass
# -> post the #community-lab claim for card 1 (one line, "for <N> h, until ~HH:MM PDT"), THEN
#    read `ettelem config` once under etsoc-shire1.lock (timeout 10), and the firmware revisions only if card 0's
#    lock is free at that moment (the stock dev_mngt_service opens both cards' management nodes)
bash tools/claims-v3/kinds/run_e82.sh smoke      # pass 8201: six 2 s runs; cycles/op 546 / 546 / 318, launch coverage
bash tools/claims-v3/kinds/run_e82.sh go 8210 6  # detached; the budget rule decides how many of the six run
bash tools/claims-v3/kinds/run_e82.sh status     # bounded checks only
```

Then copy `build/claims-v3/aifoundry1-c1/{kinds,kinds-smoke}/` and the logs to the Intel and run
`PY=/usr/bin/python3 nice -n 10 bash tools/claims-v3/kinds/collect_e82.sh 'p82[1-9][0-9]' <copy>`; copy
`build/e82-out/2026-10-31-e82-kinds-aifoundry1/` to `docs/reports/data/`, write its README (results first; registered
against happened; departures dated), and release the claim by editing it. E84 (card 0) starts only after E82 ends.
