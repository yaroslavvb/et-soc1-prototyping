# E88 — what the result path costs against the operand bits (Q130, aifoundry1 card 1) — pre-registration

*Written Sat 31 Oct 2026 (week 44), ~18:55 PDT, on the Intel, before any E88 card data exists. Frozen numbers:
[`predictions-e88.json`](predictions-e88.json); tiles, stream model and fit: [`make_e88.py`](make_e88.py) →
[`e88.json`](e88.json). Committed and pushed before the card is claimed in `#community-lab`.*

## The question

A constant (1.0 × 1.0, π × π, −1.0 × −1.0) changes no operand bit from one multiply-add to the next, and still
costs **8.1–8.5 W** in fp32 and **8.4 W** in fp16 on aifoundry3, a third of random data, and **1.56 W** in int8
(E78 README Result 2). E78's reason, "the lane is clocked and its accumulator still walks" (E78 README l.75), is
an interpretation; nothing measured it (Q130(l), the critic's item 2). E79 Result 5 adds that most of a single-bit
price is downstream of the multiplier: the same bit flip costs 7.0× more (fp32 bit 22) when the two accumulators a
lane alternates between diverge. E88 splits one random-data multiply-add's switching power into three shares, on
one card, at one clock (600 MHz, aifoundry1 card 1), in E78's frame:

| share | what switches | how E88 isolates it |
|---|---|---|
| **(i) the clocked lane** | the lane is valid and clocked; no operand and no result bit changes | constant operands with a frozen accumulator, over the type's zeros |
| **(ii) the result path** | the C read, the adder/normaliser/rounder, the result bus, the register write | the same operands with a walking result, against a frozen one |
| **(iii) the operand-side multiplier** | the operand buses and the multiplier array | moving operands with a frozen result, against constants |

## How a result is frozen while the operands move

The issue order is kinds.json fact 1.2 (PRM 9.4; `vpu_tensorfma.v:717-752`): fp32/fp16 `for k: for i: for h`,
lane `l` gets A word `[i][k]` (broadcast) and B word `[k][8h+l]` and updates C`[i][8h+l]`; int8 `for p: for i`, 16
column slots. Every micro-op is `c = a·b + c`; each C element is updated 16 times an op; the first op of a launch is
a MUL pass for its k = 0 group (`vpu_tensorfma.v:704`, `:726`), so C restarts every ~0.49 s launch (533k ops in
fp32/fp16, 895k in int8 on card 1: E82 `runs.jsonl` `iters`).

- **Absorption (fp32, and fp16 as a cross-check).** A`[:,0]` = B`[0,:]` = 2^50: the k = 0 product is 2^100, so
  after op n every C element is (n+1)·2^100, and every later product (|a·b| < 2^5) is below half an ulp (2^76): the
  multiplier runs on random mantissas and the result never changes. In fp16 the k-group-0 word (2^15, 2^15) ×
  (2^15, 2^15) gives 2^31 an op; later dot products (< 2^5) are below half an ulp (2^7).
- **Cancellation (fp16, int8).** A word (x, x) or (x, x, y, y) against B word (u, −u) or (u, −u, v, −v): every
  micro-op's dot product is exactly 0, so C stays 0. The walking partner keeps the same A and u (and v) and draws
  u' (v') independently: B word (u, −u') or (u, −u', v, −v').
- The pairs share their random draws, so the operand streams match: the model's bus-bit counts differ by 0.2%
  (fp32 r_walk/r_abs), 3.5% (fp16 r_walk/r_cancel) and 0.05% (int8); product-bit counts by < 0.8%.

`make_e88.py --check` emulates the first four ops of a launch exactly (MUL pass included) for every new tile: the
absorbed designs hold C at the k = 0 products added n+1 times, nothing else; the cancelled ones hold C = 0; the
walking ones change C every op; no tile has a zero word, so the zero gate never acts. The stream model's operand-bus
count equals kinds.json's `bus_bits_per_op` for all 51 kinds.

Rules for each tile: `e88.json` `items.<item>.rule`. Two things the counts show before any card run:
- **A constant's accumulator barely walks per micro-op.** In `ones` every C element a lane visits in one k sweep
  holds the same value, so the C read and the result bus change once every 32 micro-ops; only the register write
  changes (about 2 bits, a counter's increment). 8,671 result bits an op against random data's 124,821.
- **Random data's result path swings mostly between accumulators, not within one.** In `r_walk` the C read and the
  result bus each change ~49 bits per 8 lane-micro-ops because consecutive micro-ops visit different C elements;
  the register write adds only 8,640 bits an op. `r_het` freezes every element but keeps them different: its bus
  counts are 96% of `r_walk`'s.

## Decision rules (registered)

Every contrast is D(a) − D(b) paired within each kept pass; mean over passes, SE from the between-pass scatter, 95%
interval t(0.975, n−1)·SE. `ge thr`: PASS if the interval's low end ≥ thr, FAIL if its high end < thr, else
INCONCLUSIVE; `le` the mirror; `abs_le`: PASS if the interval lies inside ±thr, FAIL if it lies wholly outside;
`band`: PASS if the point estimate is inside the band.

| rule | test | what it means if it passes / fails |
|---|---|---|
| **H1** (fp32, fp16: W ≤ 1.0 W; int8: ≤ 0.5 W) | `le` | passes: the constant's level is the clocked lane, and "its accumulator still walks" is withdrawn as the reason; fails: the walk is a measured share and stays |
| **H2** (R32, R16 ≥ 2.0 W; R8 ≥ 1.0 W) | `ge` | passes: the result path is a large share of random data, so "power is paid for operand bits that change" is incomplete; fails: the operand bits carry it |
| **H3** (M32 ≥ 4.0 W; M16 ≥ 2.0 W; M8 ≥ 0.5 W) | `ge` | the operand-side multiplier with the result frozen |
| **H4** (M32s ≤ 1.0 W and R32s ≥ 2.0 W) | `le`, `ge` | passes: random signs (E64's +4.5 W above a constant) are paid in the result path, not the multiplier |
| **H5** ((r_het − r_abs) / (r_walk − r_abs) ≥ 0.6, per pass) | `ge` | passes: the result path's cost is mostly the C read and result bus swinging between different accumulators (E79 Result 5's hypothesis), not the walk within one |
| **H6** (\|A16\| ≤ 1.0 W) | `abs_le` | passes: absorption and cancellation freeze the result path equally in fp16; fails: one of them leaves part of the adder switching |
| **P-*** (19 bands above) | `band` | the E82-fitted three-price model, out of sample |

The **split** reported per format (the blog's numbers): D(`r_walk`) = (i) + (iii) + (ii) with
(i) = D(`c_abs`) or D(`c_cancel`), (iii) = D(frozen random) − (i), (ii) = D(`r_walk`) − D(frozen random), each in W
and in pJ per MAC through the pass's measured rate, with the per-pass share of D(`r_walk`).

## Frame, card and budget

- **Harness:** E78's runner (`kinds/run_e78.py`) and reduction (`kinds/reduce_e78.py`) run **unchanged**, with
  [`e88_common.py`](e88_common.py) in `e78_common`'s place ([`run_e88.py`](run_e88.py), [`reduce_e88.py`](reduce_e88.py),
  both refusing to run if a reused file's sha256 differs from `predictions-e88.json` `harness`); `block_e88.sh` is
  `block_e78.sh` with four marked changes (paths, the items file, the data dir `rpath/`, the smoke items). Per run:
  heat to 59 °C, launch at 58 °C after 2 s with no device process, a 4 s run of ~0.49 s launches, power window
  [t0+1 s, t0+3 s), idle bracket [t0−1.2 s, t0−0.2 s). The sampler is lib.sh's `ettelem sample --every-ms 100`,
  no `--reset-ms`.
- **Order:** per pass [pi tie] + three segments (every anchor once in each, the 16 designs dealt 6/5/5) + [pi tie],
  36 runs, shuffled with `Random("E88|aifoundry1-c1|<pass>")` (`e88_common.pass_order`).
- **Card:** aifoundry1 card 1 only (`V3_DEVICE=1`, `ET_DEVICES=1`, `/run/lock/etsoc-shire1.lock`, the `~/nekko`
  tree), 600 MHz; read-only `ettelem config` at both ends of each pass (expect TDP 65 W / 65 °C, as E82). Nothing is
  set: no governor, TDP, threshold or clock write, no `--reset-ms`, no reset. Card 0 is not used.
- **Budget:** at most **45 card-minutes**: the smoke (6 runs of 2 s: `anchor_pi`, `fp32.zeros`, `fp32.r_abs`,
  `fp32.r_walk`, `fp16.r_cancel`, `int8.r_cancel`), then passes 8810–8816 from `queue_e88.sh`, which starts a pass
  only if it ends inside 41 card-minutes of the queue's start and before 22:15 PDT (about 5.5 min a pass at E82's
  9.2 s a run: 7 passes fit). Passes 8810 onward; the smoke is 8801.
- **Primary reduction:** `reduce_e88.py` = `reduce_e78.py` unchanged with (1) E82's config-gate substitution (card
  1's 65/65) and (2) card 1's board-meter launch-gap dips removed before reduction (E82 A2's definition,
  `board_w[i] < min(board_w[i−2], board_w[i+2]) − 4 W`; on E82 they set aside two of seven passes). E78's run and
  pass gates otherwise unchanged; leakage slope `auto`. **Arms** (reported; a verdict that moves is labelled
  arm-sensitive): dips kept; leakage 0.545 (card 1's E44 idle slope), 0.3803 (E71), 0.
- **Scoring needs ≥ 4 kept passes**; with fewer, every verdict is "not scored" and the contrasts are reported as
  exploratory.

## Known limits, stated before the data

1. The "result path" here is everything a frozen result stops: the C read, the alignment of the product to C, the
   add, normalise and round, the result bus and the register write. Absorption stops the product's bits at the
   aligner (they go to the sticky bit); cancellation stops them after the dot product is formed. A16 tests whether
   that boundary matters. Neither isolates the register file from the adder; R32bus/R32sum split the bus swing from
   the walk.
2. `s_abs`'s products alternate sign, so its adder switches between effective addition and subtraction on a frozen
   result; any cost of that lands in M32s, not R32s.
3. The fp16 and int8 cancelled results are exactly 0, a special value for an adder input; the fp32 absorbed results
   are large normal numbers. F16 / F8 use C = 0, F32 uses C = (n+1)·2^100.
4. The stream model's counts are bus-level and per lane, not gate-level toggles (the RTL bench `rtl-sim/
   fma_toggle_formats` computes no correct multiply-add, Q130(b) r2 §0, and is not used). The model's prices are
   fitting constants on one card.
5. int8's stream and bus counts carry kinds.json's provisional flag (the reconstructed TIMA stream).
6. All designs are synthetic. They tell where a random multiply-add's power goes; real tensors are E86/E91.
