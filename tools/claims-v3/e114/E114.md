## The question

E84 (31 Oct) ran each of eleven kinds once in its sustained block on card 0, except fp32 zeros and random fp32, which ran
twice. So its fp16 and int8 sustained cells, and the zeros-over-random speed ratios built on them, rest on one run each:

| kind | E84 sustained rate | sampled MHz | board W | die °C | limit |
|---|---|---|---|---|---|
| fp16 zeros | 24.354 TFLOPS | 794.1 | 29.60 | 56.0 | none |
| fp16 ones | 24.395 | 795.6 | 46.72 | 63.9 | none |
| fp16 randn | 19.107 | 631.9 | 49.04 | 65.8 | thermal |
| int8 zeros | 83.709 TOPS | 794.6 | 30.87 | 56.9 | none |
| int8 full | 83.078 | 788.7 | 44.42 | 62.8 | none |

(`predictions-e114.json` › `kinds`, from E84's `results.json` › `cells`.) Zeros over random: **fp16 1.2746×, int8 1.0076×**,
one run each, against aifoundry2's 1.297× and 1.009× (E84 C4). **Do these cells, and the two ratios, hold on repeated runs,
and with what interval?** E114 runs the five kinds three times each in E84's sustained shape, on the same card, under the
same governor build, with E84's runner unchanged.

## Design

**Card and runner, as E84 had them.** aifoundry1 card 0 (`ET_DEVICES=0`, `/run/lock/etsoc-shire0.lock`). The runner is
E84's [`../kspeed/e84/run_e84.py`](../kspeed/e84/run_e84.py), unchanged (sha256 `dad381d9…`, the file E84 ran): E80's
`run_kspeed.py` and E64's `run_hpl.py` with E84's five card-0 replacements (the card, the preflight, the other-user test on
both cards, the queue drain, the configuration check against the session's own start read). The sampler runs without
`--reset-ms`. The safety stops are `run_hpl.py`'s: a die reading of 85 °C, or a board reading over 97 W on three samples.
The heater and kernel binaries are E84's (`sparsity_host` `e0fbecce…`, `sparsity.elf` `990807f4…`), and so is
`ettelem-e84` (`87c1c38c…`), all checked on the box before this registration. The tiles are Q130(s) revision 2's
(`kinds.json` `9586568f…`), each checked by sha256 by the runner before the session.

**Kinds.** fp16 zeros, ones and randn; int8 zeros and full. **No fp32**: random fp32 trips card 0's 75 W PMIC alarm
(E84). **int8 `neg_ones` is left out** under the 30 card-minute cap: its E84 cell (794.1 MHz, limit none, die 58.9 °C) is
a constant at the clock that zeros reach, and it enters no ratio.

**Blocks** ([`protocol.json`](protocol.json), order seed 114):

| block | runs | start | load |
|---|---|---|---|
| `SMOKE` | fp16 randn, int8 full, 2 s each | none | not analysed: the `file:` path, `ET_DEVICES=0`, the trace ring; no fp32 |
| `SUS` | 5 kinds × 3 passes, each pass shuffled | die reading ≤ 57 °C (300 s at most) | nine back-to-back 8 s processes (~76 s), E84's SUS unchanged |

The seeded order (`run_e84.py --list`): pass 1 fp16 randn, int8 zeros, int8 full, fp16 zeros, fp16 ones; pass 2 fp16 randn,
fp16 ones, int8 zeros, fp16 zeros, int8 full; pass 3 int8 zeros, fp16 ones, fp16 randn, fp16 zeros, int8 full.

**Time.** E84's sustained runs took 85–86 s each from one start to the next, with cooling holds of 0.1–1.9 s. Fifteen
runs are about 21.5 min. The session cap is **24 card-minutes** (`run_hpl.py` ends the session when it passes, so a run in
progress at the cap is lost, and a rule that then lacks runs reads UNDER-RESOLVED). The whole card time, claim to
release, is **at most 30 card-minutes**. The session starts only if it can start by 18:00 PST and end by 19:00.

**Order of operations** ([`run_e114.sh`](run_e114.sh)): `setup` (no device: hashes, the plan, a dry SMOKE) before the
claim; the claim; then `start`, which runs the read-only identity reads (`ettelem config` and `uptime` under the lock with
`timeout 10`; the firmware read under `timeout 10` with both cards' locks held non-blocking for the one call) and goes on
to the smoke **only if** the start read is E84's (65 W / 65 °C; release 1.4.0, BL2 0.22.0, PMIC 1.6.1), and to the session,
detached, **only if** the smoke passed its checks (exit 0, two runs, every launch rc 0, 65 W / 65 °C after each). `final`
reads `ettelem config` again after the session. Any other start read stops before the smoke, and an amendment is written
before anything else runs.

## Predictions (frozen in `predictions-e114.json`)

Each cell's mean is expected near E84's single run (context, never a verdict): fp16 zeros 24.20–24.56 TFLOPS, ones
23.80–24.56, randn 18.50–19.70 (thermal); int8 zeros 83.00–84.33 TOPS, full 82.00–84.00. fp16 ones' die reached 65 °C in
E84, so a thermal run there is possible. ρ16 is expected in 1.22–1.33 and ρ8 in 0.995–1.020.

## Decision rules (frozen; [`reduce_e114.py`](reduce_e114.py) implements them)

**Per run** the metrics are E84's, unchanged: `reduce_hpl.run_metrics` and `reduce_e84.run_extra`, imported and called as
`reduce_e84.py` calls them. The **sustained rate** is the kernel's own operations over its own wall time, for launches that
start in the last 40 s of the work (TFLOPS for fp16, TOPS for int8). **Per kind**: mean over its runs, the 95% interval
t(0.975, n − 1) · sd / √n, and the 95% prediction interval for one new run, t(0.975, n − 1) · sd · √(1 + 1/n). **Per
format**: ρ = the mean over passes of rate(zeros, pass p) ÷ rate(heavy, pass p), heavy = randn (fp16) or full (int8), with
its 95% interval over the pass ratios.

| rule | says | verdict | expected |
|---|---|---|---|
| **E114-R1** (primary) | E84's single run of each kind lies inside E114's 95% prediction interval for one run, on the sustained rate | PASS when ≥ 4 of the 5 kinds are inside; FAIL when ≥ 2 kinds with ≥ 3 runs are outside; otherwise UNDER-RESOLVED | PASS |
| **E114-R2** (primary) | fp16 zeros faster than random fp16, sustained: ρ16's 95% interval | PASS when its lower end ≥ 1.15; FAIL when its upper end < 1.15; otherwise INCONCLUSIVE; UNDER-RESOLVED below three pairs | PASS (point 1.2746) |
| **E114-R3** (primary, a reading) | int8 zeros against int8 full, sustained: ρ8's 95% interval | FASTER (lower end > 1), SLOWER (upper end < 1), SAME_WITHIN_BAR (holds 1 and lies inside [0.98, 1.02]), otherwise INCONCLUSIVE; UNDER-RESOLVED below three pairs; RIGHT when the reading equals the frozen one | SAME_WITHIN_BAR |
| **E114-R4** (primary) | the limiting test replicates: each run's sustained limit (`reduce_e84.run_extra`'s label, unchanged) equals E84's for its kind (fp16 randn thermal, the other four none) | PASS when at most 1 of ≥ 14 runs differs; FAIL when ≥ 2 differ; otherwise UNDER-RESOLVED | PASS |
| **E114-S1** (secondary) | card 0's ρ against aifoundry2's ratio of mean sustained rates over its committed runs (E80, E83, E87, E96: fp16 zeros 4 runs, randn 6; int8 zeros 4, full 8): Δ = ρ(card 0) − ρ(aifoundry2), 95% interval t(0.975, df) · √(se₀² + se₂²), df = the smaller of card 0's pairs and aifoundry2's smaller count, minus 1; se₂ by the delta method | ALIKE when the interval lies inside ±0.05 (fp16) or ±0.02 (int8); DIFFERENT when it excludes 0; otherwise INCONCLUSIVE | fp16 DIFFERENT (card 0 lower: its random fp16 draws less power and throttles less while both cards' zeros sit near the 800 MHz cap; three pairs may not resolve it); int8 INCONCLUSIVE |

**Context, never a verdict**: each cell's sampled clock, non-ramp clock, board W, die mean and maximum, ramp share and
limit, with intervals and E84's run beside; the pass-paired zeros-minus-heavy sustained clock per format (E84-P1's form);
today's heat path against 31 Oct's (each run's die minus E84's die line at its board W, 41.780 + 0.4753 °C per W over E84's
13 sustained runs); ρ as the ratio of the two cells' mean rates; the idle level and the cooling gates.

**Under-resolved**: a kind with fewer than three runs is not scored in R1, a format with fewer than three pairs reads
UNDER-RESOLVED in R2/R3, and R4 needs 14 runs to PASS; a FAIL already decided by the runs present stands.

## Departures from E84's design, named

1. Five kinds, fp16 and int8 only (no fp32: the 75 W alarm; no int8 `neg_ones`: the cap).
2. The sustained block three times, each pass shuffled; no burst block (E84 ran one sustained pass, with second runs for
   fp32 zeros and random fp32 only).
3. The smoke runs fp16 randn and int8 full (E84's included random fp32).
4. A 24 card-minute session cap (E84: 60), inside 30 card-minutes claim to release.
5. The firmware read under `timeout 10` (E84 used `timeout 20`; its correction C5 asked for 10), and a `start` stage that
   checks the start read and the smoke before going on (E84 ran its stages by hand).
6. Output in `build/e114` on the box, data in `docs/reports/data/2026-11-01-e114-card0-replicates/`.
7. A new reduction for the cells and rules (`reduce_e114.py`); its per-run metrics are E84's code, unchanged. On E84's own
   session it reproduces E84's five single runs exactly (rate, clock, W, die, limit, ramp share), with every rule
   UNDER-RESOLVED (one run each).

`run_e84.py` writes the session's `e84.json` with E84's name and E84's `predictions.json` hash: that is the unchanged
runner speaking. The stage script sets `E84_FREEZE` to E114's freeze commit, so that file carries it, and writes
`e114-start.json` (E114's hashes) beside the session.
